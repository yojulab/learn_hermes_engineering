## 1. AI 사용 목적

- 상태: ✅ 결정

## 2. 모델 선택

### 모델 및 실행 방식
- 상태: ✅ 확정 (2026-08-11 팀회의 — 얼굴 파이프라인 5종)
- 결정 — **얼굴 파이프라인 5종 (역할별)**:

  | 역할 | 모델 | 실행 위치 | 비고 |
  |---|---|---|---|
  | 탐지 | **YuNet** | **카메라(Jetson Nano) 탑재** | 얼굴 위치만. 경량 |
  | 식별(앙상블) | **ArcFace-R100(glint) + AdaFace-ir101** | **GPU 서버** | 2026-08-13 재벤치마크로 확정 — AdaFace+R100 95.8%(신규 실측, 최고) (99_DECISIONS 참조) |
  | 정렬·포즈 | **MediaPipe** (468점) | GPU 서버 | 식별 아님 — 정렬/각도 측정 보조 |
  | 정면화 | **TP-GAN** | GPU 서버 | 식별 아님 — 고도화(다음 주)·검증 후 도입 |

  - **⚠ "식별 모델"은 실제로 ArcFace-R100 + AdaFace-ir101 2개다.** MediaPipe(포즈)·TP-GAN(정면화)은 임베딩을 만들지 않으므로 식별자가 아니라 전처리 보조. "5종=4식별"이 아님.
  - **결합 방식**: ✅ **score fusion 확정** (2026-08-11 실측 — fusion=voting 동률이나, 확정 앙상블이 2모델이라 voting은 1:1 동점이 잦아 무의미. fusion이 모델 수 변화에 유연·단순. 아래 3장 결합 방식 실측)
    - 서빙에서의 fusion은 **raw 코사인 평균**이다(임계값 0.40) — z-score 합은 미등록자를 거를 수 없어 2026-08-13에 교체했다. 아래 "서빙 원트랙 전환" 참조
  - **서빙 형식**: 둘 다 `.onnx` + `onnxruntime` (서버에 torch 불필요 — 이슈 #88). AdaFace는 `tools/export_adaface_onnx.py`로 `.pt`에서 변환한다
  - **추론 환경**: 탐지=Jetson, 식별 앙상블=학원 GPU 서버. Jetson은 무거운 앙상블을 지지 못하므로 역할 분리
  - **⚠ 라이선스**: ArcFace-R100·AdaFace-ir101 **둘 다 비상업 연구 전용**(insightface/AdaFace 사전학습 모델). 학원 발표·포트폴리오는 무방, 실서비스는 재검토. SFace(Apache-2.0)는 고각 저하로 제외되며 상업 가능성도 함께 잃음
  - **R50→R100 전환 경위 (2026-08-12 → 2026-08-13 재확인, 이슈 #84)**: 08-12 시점엔 `w600k_r50.onnx` 원본이 CTO 로컬에도 팀원 로컬에도 확인되지 않아 R100(`glintr100.onnx`, 검증 완료: 원본 대비 코사인 유사도 0.9999998)으로 임시 전환했었다. **08-13 정정**: 파일은 실제로 CTO 로컬에 있었고(3차 실측 8/11에 쓴 그 파일), 드라이브 인수인계 목록에서만 누락된 것 — "리포에 없어서"가 아니라 "공유 경로 누락"이 정확한 사유다(이슈 #84). 같은 날 CTO가 개인 전달, SHA256 해시 대조로 원본 동일성 확인 완료.
    **재벤치마크 결과(2026-08-13, 아래 4차 실측)**: 그동안 한 번도 측정된 적 없던 **"AdaFace+R100" 2모델 조합이 95.8%로 전체 최고** — 기존 확정이던 R50+AdaFace(94.9%)는 물론 3모델 조합(95.5%)보다도 높다. 이 실측 결과로 **R100+AdaFace 유지를 재확정** — 이번엔 "R50 파일이 없어서"가 아니라 **실측 근거**가 사유다.
  - **LLM**: ✅ **gemma4:26b 확정** (2026-08-10) — 학원 GPU 서버 Ollama 구동. 툴콜·한국어·범위 밖 방어 실측 통과(VRAM 19/46GB, 응답 2초 내). qwen3는 한국어 질의 중 중국어 누출로 제외 (specs/14 6장)
- 결정일: 2026-08-05 (비전 툴 08-06 → 앙상블 확정 2026-08-11)

### 얼굴 식별(누구인지 판단)·라벨링 방식
- 상태: ✅ **확정 (2026-08-13 갱신) — 앙상블 ArcFace-R100(glint) + AdaFace-ir101** (아래 4차 실측 근거, 이슈 #84)
  - ⚠ 2026-08-11 최초 확정은 R50+AdaFace였고, 08-12엔 자산 문제로 R100+AdaFace로 임시 전환했었다. 08-13 재벤치마크로 **R100+AdaFace(95.8%)가 실측상 최고**임을 확인해 같은 조합을 실측 근거로 재확정했다 — 아래 3차·4차 실측 두 표 다 참고할 것(3차는 R50 단독 특성 확인용으로 유효, 최종 앙상블 선택은 4차 기준)
- 결정: **탐지 YuNet + 식별 앙상블(ArcFace-R100 + AdaFace-ir101) + 동의자 사전 등록·코사인 유사도 매칭**

- **3차 실측 (2026-08-11 — 모델 5종 후보 + 앙상블, 세션 분리 9~10명)**:

  | 모델(단일) | top-1 | 분리도 | 라이선스 |
  |---|---|---|---|
  | ArcFace-R50 | **94.9%** | +0.463 | 비상업 |
  | AdaFace-ir101 | **94.9%** | **+0.492** | 비상업 |
  | ArcFace-R100(glint) | 93.8% | +0.505 | 비상업 |
  | AdaFace-ir50 | 91.5% | +0.412 | 비상업 |
  | SFace | 89.8% | +0.372 | Apache(상업) |

  | 앙상블(score fusion) | top-1 |
  |---|---|
  | AdaFace-ir101 + R50 | 94.9% |
  | AdaFace-ir101 + R50 + R100 | **95.5%** |

  - **팀이 지목한 "AdaFace 고각 강함"이 실측으로 확인됨** — 단, **ir101 기준**(ir50은 91.5%로 낮음). 백본 버전이 3.4%p를 가른다.
  - **앙상블은 단일 대비 +0.6%p** — 여러 모델이 다른 실수를 상쇄.

- **4차 실측 (2026-08-13 — 이슈 #84 대응, "AdaFace+R100" 미실측 조합 채우기)**: `w600k_r50.onnx` 원본을 CTO에게 재전달받아(해시 대조 완료) `webapp/tools/finetune/`용 정리 데이터셋(`선분류_0807_clean`, 인물 10명 세션분리 조건 충족 — 3차 실측과 동일 인원수 대역)으로 재실측. 단일 모델 값이 3차 실측과 정확히 일치해 파이프라인 재현성을 확인했다:

  | 모델(단일) | top-1 | 분리도 | 비고 |
  |---|---|---|---|
  | ArcFace-R50 | 94.9% | +0.464 | 3차 실측과 동일 — 재현 확인 |
  | AdaFace-ir101 | 94.9% | +0.493 | 3차 실측과 동일 |
  | ArcFace-R100(glint) | 93.8% | +0.505 | 3차 실측과 동일 |
  | SFace | 90.1% | +0.374 | 3차 실측과 동일 |

  | 앙상블(score fusion) | top-1 | 비고 |
  |---|---|---|
  | R50 + AdaFace-ir101 | 94.9% | 기존 확정 조합 |
  | **R100 + AdaFace-ir101** | **95.8%** | **⚠ 이슈 #84가 지적한 미실측 조합 — 전체 최고, 이번에 처음 측정** |
  | AdaFace-ir101 + R50 + SFace | 95.2% | |
  | AdaFace-ir101 + R50 + R100 | 95.5% | 3차 실측과 동일 |
  | AdaFace-ir101 + R50 + R100 + SFace | 95.5% | |

  - **R100+AdaFace(95.8%)가 R50+AdaFace(94.9%)는 물론 기존 최고였던 3모델 조합(95.5%)보다도 높다** — 2026-08-12 "R50 파일이 없어서" 임시 전환했던 R100+AdaFace가, 실은 실측 기준으로도 최선의 선택이었음이 이번에 처음 확인됨.
  - 표본 10명 규모(세션분리 조건 충족 인원 기준)라 오버피팅 여지는 3차 실측과 동일하게 남아있음 — 등록 도구(#80·#81) 이후 데이터가 쌓이면 재검증 권장.
  - ⚠ **95.8%를 인용할 때 8차 실측(이슈 #128)을 같이 볼 것** — 정리 전 원본 데이터셋에서는 같은 기준으로 **94.5%**다. 모델 서열(R100+AdaFace 최고)은 유지되지만, 절대값은 데이터 구성에 ±1%p 이상 흔들린다

- **✅ 서빙 원트랙 전환 (2026-08-13)**: SFace를 걷어내고 **등록·조회 모두 앙상블**만 쓴다 (99_DECISIONS). 근거는 아래 5차 실측이다.
  - **fusion은 z-score 합이 아니라 raw 코사인 평균**이다. 폐쇄집합(등록자만 들어온다는 가정)에서는 둘 다 top-1 98.9%로 같지만, 실서비스는 **미등록자가 압도적으로 많다**(동의자 11명 외 전원이 카메라를 지나간다). z-score는 갤러리 축 위 상대값이라 미등록자에게도 큰 격차가 생겨(실측 최고 margin 4.62 > 임계 4.05) 절대 임계값을 세울 자리가 없다.

    | fusion | 등록자 통과 | 미등록 오통과 |
    |---|---|---|
    | **raw 코사인 평균 @0.40** | **95.8%** | **0.0%** |
    | z-score margin @4.05 | 93.9% | 1.0% |
    | (참고) SFace @0.41 | 83.3% | 0.3% |
  - `identification.EnsembleIdentifier`는 z-score 방식이라 **서빙 경로에서 쓰지 않는다** — 매칭은 `registry.FaceRegistry.match`가 한다. 벤치마크(폐쇄집합)에는 그대로 유효하다.
  - **AdaFace는 `.onnx`로 서빙한다** (`tools/export_adaface_onnx.py`, 원본 대비 코사인 1.00000000). 서버에 torch가 필요 없어진다 — 이슈 #88 이중 트랙 결정의 실행. 성능(컨테이너): 탐지 9.4ms/프레임, 앙상블 임베딩 167ms/얼굴
  - ⚠ **임계값 0.40은 등록자 11명 기준이다.** 사람이 늘수록 남과 닮을 기회가 늘어 미등록자 최고점이 올라간다(현재 최고 0.343). 등록 인원이 늘면 재측정할 것

- **5차 실측 (2026-08-13 — 실등록자 갤러리 검증)**: 위 재검증 권장에 대한 응답. 4차까지는 정리 데이터셋(수집·선분류한 프레임)이었지만, 이번엔 **SCR-004로 실제 등록한 11명의 보관 사진 330장**이 대상이다 — 서비스가 실제로 쓸 갤러리 그 자체다.
  - **프로토콜**: 갤러리 = 정면(front) 6장 / 조회 = 나머지 4방향 264장. 같은 날·같은 조명이라 세션분리는 아니지만, **등록에 쓰지 않은 각도로만 조회**하므로 "같은 사진을 양쪽에 넣는" 부풀림은 없다. 상한치로 읽을 것.

  | 방식 | top-1 | 숙임(down) | 들기(up) | 좌(left) | 우(right) |
  |---|---|---|---|---|---|
  | **앙상블 R100+AdaFace (fusion)** | **98.9%** | 95.5% | 100% | 100% | 100% |
  | SFace 단독 (현행 서빙) | 93.2% | 86.4% | 86.4% | 100% | 100% |

  - **좌우는 동률, 상하에서 갈린다** — 출입 카메라는 위에서 내려다보므로 실전 각도가 정확히 그쪽이다. 앙상블 전환의 실익이 여기 있다.
  - ⚠ **현행 SFace 임계값 0.41이 genuine의 16.7%(44/264)를 미매칭으로 떨어뜨린다** (impostor 오통과는 0.3%). 임계값이 "안전한 쪽"으로 과하게 잡혀 있어 **등록자를 못 알아보는 쪽으로 실패**하고 있다 — 미퇴실자를 놓치는 방향이라 기능 목적에 직접 반한다. 앙상블 전환과 함께 임계값 재산정 필요.
  - 앙상블 fusion 점수는 z정규화라 절대 임계값이 없다. 대신 **1위-2위 격차**가 미등록자 판정 후보 지표다 — 실측 중앙값 5.27, 5퍼센타일 3.77, 최저 0.59.
  - 앙상블 오식별 3건은 모두 윤혜진·방우리·최진영 3인 사이에서 발생. 등록자 수가 늘면 이런 근접 쌍이 늘어나므로 세션 2회 등록(다른 날 [추가 촬영])의 값어치가 커진다.
  - 갤러리 구축: `tools/backfill_ensemble_gallery.py` (보관 사진 → `registered_faces`의 앙상블 2필드, rules/04)

  - **결정: 서빙 미적용 유지.** 운영 임계값 0.40 고정 비교(이슈 #135의 규칙)에서 미등록 오통과가 2.4배로 — 문자 오발송 직결 지표가 무너진다
  - **단, 원인은 식별력 저하가 아니라 점수 분포의 상향 압축이다.** 11명만으로 학습한 InfoNCE 헤드가 등록자·미등록자를 다 같이 끌어올렸다 — 미등록 최고 유사도 **0.607 → 0.743**. 학습에 없던 낯선 사람일수록 이렇게 끌려 올라간다면 **등록 인원이 늘 때 먼저 무너지는 방향**이다
  - **같은 오통과 수준끼리 맞추면 오히려 낫다**: 오통과 4.4% 기준 원본 72.6%(임계 0.45) vs 파인튜닝 **76.7%**(임계 0.50), 3.0% 기준 65.3%(0.50) vs **72.6%**(0.55). **ROC상 개선은 실측 사실이다** — "파인튜닝 무용" 결론이 아니다
  - **그런데 채택하려면 임계값을 0.50대로 재조정해야 하고, 그 근거가 없다.** 재조정을 정당화할 미등록 표본이 **3명·135장**뿐이다(6차의 그 경고 그대로). → **트랙은 접지 않고 보류** — 미등록 표본 보강 후 0.50 재조정과 함께 재검토
  - 읽을 때 주의: 평가 로그의 `RuntimeWarning: divide by zero/overflow in matmul`은 `registry.py`에 문서화된 **macOS BLAS 오탐**이다. 다만 억제하지 말라는 이유 그대로, 이번에도 파인튜닝 임베딩 10장을 전수 검사(NaN/Inf·L2 정규화)해 진짜 NaN이 아님을 확인하고 나서 수치를 읽었다
  - ⚠ 옮기며 밟은 함정: R100의 torch dynamo exporter(opset 18)는 가중치를 **`<이름>.onnx.data` 외부 파일로 분리 저장**한다(.onnx 자체는 498KB 그래프뿐). `.onnx`만 scp하면 로드가 `No such file: ….onnx.data`로 실패한다 — **두 파일을 함께 옮길 것.** 구식 exporter를 쓰는 `export_adaface_onnx.py` 산출물(AdaFace)은 단일 파일이라 해당 없음

- **✅ A 고도화 — 비율 검사(open-set margin) 채택 (2026-08-18, 서빙 반영)**: open-set 거절을 1등 절대 임계값 하나에서 **"1등 절대값 AND 1등−2등 격차(margin)"**로 확장했다. 낯선 사람은 여러 등록자와 고만고만하게 닮아 격차가 작고(거절), 본인은 한 명한테만 확 닮아 격차가 크다는 가설을 6차와 **같은 조건**(등록 897/미등록 135장)으로 실측 검증했다.

  | 방식 | 등록자 통과 | 오식별 | **미등록 오통과** |
  |---|---|---|---|
  | 6차 기준 (임계값 0.40만) | 78.1% | 3.9% | **11.9%** |
  | **A 고도화 (0.38 + margin 0.10)** | 76.6% | 2.3% | **3.7%** |

  - **핵심: 통과율을 78.1→76.6%로 1.5%p만 내주고 오통과를 11.9→3.7%로 8.2%p 낮췄다.** 임계값 단독으로 같은 오통과(3.7%)에 도달하려면 통과율이 훨씬 더 떨어진다(0.50에서 65.3%) — margin이 절대 임계값보다 정밀하게 거절 일을 한다. 이긴 조합이 임계값을 **낮추고**(0.40→0.38) margin을 얹은 형태인 것도 그 증거: 절대 바를 낮춰 개성 있는 본인은 살리고, 격차 게이트로 낯선 사람을 거른다
  - **SFace 시절 후보였던 "1위-2위 격차"(위 2차 실측 참조)를 raw 코사인 서빙에서 정식 검증·채택한 것이다.** 그때는 z정규화라 절대 임계값이 없어 보류됐고, 지금은 raw 코사인 평균이라 절대 임계값과 격차를 함께 쓴다
  - 구현: `registry.match`가 `registry.rank`(서빙·평가 공용 스코어링)로 top-2를 얻어 두 조건을 함께 본다. `MATCH_MARGIN`(기본 0.10)·`MATCH_THRESHOLD`(기본 0.38) 설정값. 등록자 1명이면 2등이 없어 margin 자동 통과
  - ⚠ **잠정 채택 — held-out 재확인 필요.** margin은 새 하이퍼파라미터라 이 평가셋(미등록 3명·135장)에 과적합됐을 수 있다. 오통과 절대값 3.7%도 그 표본 한계를 그대로 진다 — **미등록 표본 보강 후 held-out으로 margin을 재조정**할 것. 상대적 우위(비율검사 > 임계값 단독)는 구조적이라 견고하다
  - **회귀 게이트가 margin을 소유한다** — `baseline.json` 조건에 `margin` 필드 추가, `eval_openset.report(rows, threshold, margin)`. 모델·정렬·갤러리를 바꾸는 PR은 이제 이 운영점(0.38+0.10)과 대조된다
  - ⏭ **회전 증강은 같은 날 기각** — 등록 사진을 정렬 이전 회전시켜 갤러리에 더하면 통과율은 +1.9%p 오르나 **오통과가 11.9→18.5%로 폭증**한다(갤러리를 파생본으로 부풀리면 낯선 사람도 더 잘 걸린다 — max-over-gallery 스코어링). 단 이는 **갤러리 레벨** 결론이고, 인코더를 개선하는 **파인튜닝 레벨** 회전 증강은 별개다(→ 파인튜닝 트랙에서 재검증)

- **✅ C-1 고도화 — 갤러리 집계 top-k 평균 (2026-08-19 실측·채택, 운영 기본값 전환)**: 한 인물의 장별 유사도를 **최댓값**으로 접던 것을 **상위 k개 평균**으로 넓혔다. `MATCH_TOPK=1`이면 최댓값과 **비트 단위로 같다**(이전 동작).

  **실측·채택 (2026-08-19 저녁, specs/16 §5·§6)**: A/B/C 비교에서 §6 규칙(오통과→통과→오식별)으로 **승** — 운영 기본값을 `th 0.35 + k 5 + margin 0`(공격안)으로 전환했다. 실측 **80.8 / 1.2 / 17.9 / 0.7** (기준선 78.1/3.9/—/11.9와 A 76.6/2.3/21.1/3.7을 **모든 지표에서** 상회). A+C 결합은 오통과가 0.7%에서 더 안 내려가고 통과만 −3.0%p — **margin의 몫을 top-k가 점수 단계에서 흡수**한 것이 실측됐다(직교 기각). margin 코드는 은퇴가 아니라 0으로 대기 — 표본 보강 재측정에서 다시 유효할 수 있는 독립 손잡이다. ⚠ 공격 운영점 0.35는 미등록 상위 1% 유사도(0.349)와 간발 — **등록 인원이 늘면 최우선 재측정**(보수 대안 0.38, specs/16 각주).

  - **가설 — max는 극단값 추첨이다.** 인당 30장 × 등록 11명 = **330번의 추첨**이고, 낯선 사람도 그중 한 장의 조명·각도와 우연히 맞으면 그 한 장이 그 사람의 점수가 된다. 본인은 자기 얼굴이라 여러 장과 고르게 닮으므로, 평균을 내면 **우연만 희석되고 본인은 남는다**. A(비율 검사)가 1등−2등 **격차**로 같은 문제를 봤다면, C-1은 **1등 점수가 만들어지는 방식** 자체를 손댄다 — 그래서 둘은 직교할 수 있다(목요일 A+C 줄이 그 확인이다)
  - ⚠ **k의 상한은 "방향당 장수"다.** 갤러리는 5방향(front·left·right·up·down) × 6장 구성이라 k>6이면 방향을 넘어 평균하게 되고, 그러면 위 `match()` 경고가 말하는 **"어느 쪽과도 닮지 않은 값"**이 된다(전체 평균을 안 쓰는 이유 그대로). **후보 구간은 k=3~5**
  - 구현: `registry._aggregate()` 하나다. `rank()`가 이걸 경유하므로 서빙(`match`)·평가(`eval_openset`)·회귀 게이트가 **자동으로 같은 집계**를 쓴다. `topk <= 1`은 `np.max`로 **따로 뺐다** — 1개짜리 평균은 수학적으로 같지만 float64를 경유하며 마지막 비트가 달라질 수 있고, 기본값이 종전과 **완전히** 같아야 회귀 게이트를 근거로 쓸 수 있다(실규모 11명×30장×512차원 200회 전수 일치 확인)
  - ⚠ **topk는 sweep 대상이 아니다.** margin은 top-1·top-2만 보므로 `report`에서 훑을 수 있지만, topk는 **점수 자체**를 바꿔 `rank`를 다시 태워야 한다 — k 값마다 재실행이고 임베딩이 다시 돈다. k를 3~5로 좁게 잡은 실무적 이유이기도 하다
  - **회귀 게이트가 topk를 소유한다** — `baseline.json` 조건에 `topk` 필드(margin과 같은 방식). 채택과 함께 기준선을 **`th 0.35 + m 0 + k 5` 운영점으로 재측정·이관**했다 — 모델·정렬·갤러리를 바꾸는 PR은 이제 이 운영점과 대조된다

- **결합 방식 실측 (2026-08-11 — score fusion vs voting, 세션 분리)**:

  | 조합 | 단일 최고 | score fusion | voting |
  |---|---|---|---|
  | R50 + AdaFace-ir101 | 94.9% | 94.9% | 94.9% |
  | R50 + AdaFace + R100 | 94.9% | 95.5% | 95.5% |

  - **정확도로는 fusion=voting 동률.** 선택 기준은 운영성. **확정 앙상블이 2모델**이라 voting은 1위가 1:1로 갈려 사실상 fusion과 같아진다(홀수 모델에서만 voting이 자연스러움).
  - **→ score fusion 확정.** 유사도 z정규화 후 합산 → argmax. 모델 추가·제거에 코드 불변이라 유연.

**설계에서 의도적으로 정한 것 3가지**

1. **배경 세그멘테이션은 하지 않고, 저장은 대상자 중심 1.8배 크롭이다** (2026-08-12 실기기에서 확정).
   - 세그멘테이션(누끼)을 안 하는 이유: 등록만 배경을 지우면 조회(CCTV는 배경 그대로)와 조건이
     어긋나고, 턱선·머리카락을 자른 자리가 임베딩을 흔든다. 화면의 타원 밖 어둡게는 UI 효과일 뿐
   - **전체 프레임도 저장하지 않는 이유**: 실기기 검증에서 배경(모니터/포스터/뒤 사람)의 다른 얼굴이
     전 사진에 함께 저장됐다 — 동의자 등록 사진에 **비동의자 얼굴이 들어가는** rules/04 문제이고,
     `register_faces.py`의 "단독 얼굴만" 요건에도 전부 걸려 등록이 0장 처리됐다.
     대상자 bbox 1.8배 크롭이면 재임베딩(alignCrop 112×112)에 충분하고 배경 얼굴은 잘려 나간다
     — detection_records가 원본 프레임 대신 확장 크롭을 쓰는 것과 같은 결정이다
2. **중립 자세를 사람마다 실측해서 쓴다** — **정면 단계에서 관측한 pitch 중앙값이 그 사람의 중립**이고,
   상/하는 전부 그 기준으로 판정한다. 고정값(0.57)은 *CCTV 크롭*에서 나온 값이라 눈높이 웹캠에는
   맞지 않아 **상/하가 영영 통과되지 않았다**(2026-08-12 실기기). 그래서 정면 판정은 yaw만 본다 —
   거기서 잰 pitch가 곧 중립이기 때문이다. `--base-pitch`는 정면을 건너뛸 때의 폴백으로만 남는다
3. **자세보다 품질 게이트를 먼저 본다** — 거리·중심·밝기·흔들림(라플라시안 분산)을 통과해야
   자세를 판정한다. 등록은 조회의 **기준이 되는 데이터**라 CCTV보다 엄격해야 한다

**⚠ 한 자리에서 연속 촬영하는 것의 한계** — 08-06 실측에서 등록을 한 세션으로만 만들면 교차 세션
유사도가 0.93 → 0.31로 급락했다. 5방향을 앉은 자리에서 찍으면 조명·옷·시간이 전부 같다.
→ 도구가 중복을 제거하고, 끝에 **다른 날 1회 추가 등록**을 권한다.
실제 등록 운영 규칙은 여전히 **"인당 5~10장 + 세션 2개 이상"**이다.

**⚠ 임계값은 CCTV 실측에서 그대로 가져오면 안 된다 (2026-08-12 실기기 정정)**
- **중복 제거 0.55 → 0.97**: 0.55는 *여러 자세가 섞인 등록 영상 전체*에서 대표를 뽑을 때 쓴 값이다
  (719장→17장). 이 도구는 *한 방향에서 자세를 유지한 채* 여러 장을 담으므로 프레임끼리 유사도가
  0.9를 넘는 게 정상이고, 0.55로는 **첫 장 이후 전부 버려져 진행이 멈춘 것처럼 보였다.**
  자세 다양성은 임계값이 아니라 **방향 단계가 만든다**
- **거리·선명도·각도도 완화**: 얼굴 폭 목표 0.34→0.26(0.34는 노트북에 바짝 붙어야 했다),
  선명도 60→25(웹캠은 압축이 있다), 좌우 각도 0.25→0.18(많이 돌리면 YuNet이 얼굴을 놓쳐 되레 막힌다),
  **상/하 0.18→0.07** — 이 프록시는 가동 범위가 좁아(20° 숙여도 0.11 남짓) 크게 잡으면 못 닿는다
- **`--relax` 배율**로 현장에서 더 풀 수 있다. 화면에 실시간 `yaw`·`pitch`를 띄워 **왜 안 넘어가는지**를
  눈으로 보고 조정한다
- **SPACE = 수동 촬영**(품질 게이트는 통과해야 한다). 프록시는 얼굴 생김새·카메라 위치에 따라
  반응이 달라 자동 판정만으로는 언제든 다시 막힐 수 있다 — **도구가 멈추지 않게 하는 탈출구**다

- 자세는 **YuNet 5점 랜드마크 프록시**(실측 스크립트와 같은 식)로 잰다 — 정밀 각도가 아니라
  "충분히 돌았나"를 본다. MediaPipe 468점을 도입하면 더 정밀해진다
  - ⚠ **부호를 두 번 뒤집은 이력이 있다** — 만지기 전에 코드 주석(`Pose`)을 읽을 것.
    확정: **yaw `+` = 왼쪽**, **pitch가 클수록 숙인 것**(코가 앞으로 튀어나와 `pitch = d/D + (p/D)tanθ`.

#### 운영 탐지 루프의 처리 주기를 AIMD로 조절 (2026-08-14 구현 — `app/services/detection.py`)

`DetectionPipeline._run()`이 `DETECTION_INTERVAL_SECONDS` 고정값으로만 돌아 처리 부하와
무관하게 항상 같은 주기로 `process_all()`을 불렀다 — 카메라가 늘거나 GPU가 다른 작업과
경합해도 간격이 그대로라, 여유가 있어도 느리게 돌고 과부하여도 그대로 밀어붙였다. AIMD(Additive
Increase/Multiplicative Decrease, TCP 혼잡 제어와 같은 원리)로 스스로 조절하도록 바꿨다.

- **신호는 `FaceEngine.extract()` 처리시간 합**(카메라별 순차 처리 전체)만 쓴다 —
  `record_crop`·이벤트 저장·Spring 발행 같은 I/O 시간은 섞지 않는다(GPU 바운드 신호를
  흐리지 않기 위함). EWMA(`EWMA_ALPHA=0.1`)로 스무딩해 지속적으로 간격의 80%(`HIGH_LOAD_RATIO`)를
  넘기면 간격을 배수(`INTERVAL_GROW=1.5`)로 늘리고(fps 급감), 30%(`LOW_LOAD_RATIO`) 밑이면
  조금씩(`INTERVAL_SHRINK=0.95`) 줄인다(fps 완만 증가, 진동 방지).
- **상한은 `DETECTION_INTERVAL_SECONDS`(기존 설정값), 하한은 신설한
  `DETECTION_MIN_INTERVAL_SECONDS`(기본 0.2초)다.** 시작값은 **상한**(가장 느린/안전한
  값)으로 잡는다 — 기동 직후 부하를 모르는 채로 곧장 빠르게 돌면 첫 사이클부터 GPU를
  과부하시킬 수 있어, 오늘까지의 고정값(1초)에서 시작해 여유가 실측될 때만 빨라지도록 했다.
- 현재 간격은 `DetectionPipeline.current_interval` 프로퍼티로 노출하고
  `status_snapshot()`(API-011)에도 `interval_seconds`로 실어 관측 가능하게 했다.
- 단위 테스트는 `webapp/tests/test_detection.py`의 `test_AIMD_*` 3건 — 초기값이 상한인지,
  여유 상태에서 줄어드는지, 지속 과부하에서 다시 상한까지 늘어나는지를 가짜 엔진(즉시
  반환·`time.sleep`)으로 검증(GPU 없이).

  1차는 같은 영상의 연속 프레임을 시간순으로 나눠 사실상 인접 순간끼리 비교한 것이라 과대평가였다.

  | 임계값 | 정확도 | 오매칭 | 미매칭 |
  |---|---|---|---|
  | 0.30 | 52.0% | **43.5%** | 4.5% |
  | 0.35 | 47.5% | 31.6% | 20.9% |
  | **0.41** (기존 채택값) | **27.1%** | 17.5% | 55.4% |
  | 0.45 | 18.6% | 12.4% | 68.9% |
  | 0.50 | 7.3% | 3.4% | 89.3% |
  | 0.55 | 3.4% | 0.6% | 96.0% |

  **→ 사용 가능한 임계값이 존재하지 않는다.** 낮추면 절반이 오매칭(0.30에서 43.5%), 높이면 대부분 미매칭(0.50에서 89.3%).

  **근본 원인 — 클래스 간 거리 < 클래스 내 거리**: 임계값 문제가 아니라 임베딩 분리도 자체가 무너져 있다.

  | 항목 | 값 |
  |---|---|
  | 다른 사람인데 임계 초과 | 인물A↔인물B **0.524**, 인물A↔인물C 0.451, 인물D↔인물E 0.414 |
  | 같은 사람 내부 평균 | 인물B 0.345, 인물D 0.370, 인물A 0.472 |
  | 같은 사람·다른 세션 최저 | 인물F **0.161**, 인물G 0.191, 인물H 0.268 |

  "다른 사람끼리 닮은 정도(0.52)"가 "같은 사람끼리 닮은 정도(0.35)"보다 크다 — 이 상태에서는 어떤 임계값도 성립하지 않는다.

  **원인 분석**: 데이터 부족이 아니라 **촬영 조건**으로 보인다.
  - CCTV 하향 각도 — 천장에서 내려다봐 정면 얼굴이 거의 없다. SFace는 정면 정렬 전제로 학습된 모델이다
  - 해상도 — 10편 중 5편이 640×480. 크롭 중간 크기 110~162px로 SFace 입력(112px)을 겨우 넘긴다
  - 참고: 저해상도 5편의 **얼굴 검출률이 오히려 65~85%로 1080p(14~29%)보다 훨씬 높았다** — 촬영 거리가 가까웠기 때문. 즉 "검출"은 되지만 "식별"이 안 되는 상태

  **선택지 (CTO 판단 대기)**:
  1. **카메라 각도 하향 조정 후 재촬영** — 근본 대응. 얼굴 높이에 가깝게 설치
  2. **등록용 정면 사진 별도 촬영** — CCTV로 등록부까지 만들지 않고 동의자 정면 사진으로 등록 (일반적인 얼굴인식 운영 방식)
  3. **ArcFace 동일 조건 재측정** — 각도 강건성이 나을 가능성. 단 비상업 라이선스 제약
  4. **시연 범위 조정** — 식별 대신 "사람 감지"까지만. LMS 태그가 primary이므로 구조상 성립 (rules/05 안전장치)

  **⚠ 이 결과가 확정될 때까지 `MATCH_THRESHOLD=0.41`(.env·webapp config)은 "임시값"으로 취급한다.** 그 값으로 운영하면 절반 이상을 놓치고 17.5%는 엉뚱한 사람으로 매칭한다

- 결정일: 2026-08-06 (툴 선정) / 2026-08-07 (정확도 근거 무효화·재검토 착수)

### ⚠ 모델 교체 → 갤러리 재구축 → 기동 순서 (필수 체크리스트, 2026-08-14 · 이슈 #118)

**식별 모델을 바꾸면 `registered_faces`의 앙상블 임베딩(`arcface_embeddings`·`adaface_embeddings`)도 반드시 다시 만들어야 한다.** 이 임베딩은 그것을 뽑은 모델에 묶여 있다. 모델만 바꾸고 갤러리를 그대로 두면 조회 쪽은 새 모델로 임베딩을 뽑는데 갤러리는 옛 모델 기준이라, **서버는 정상 기동하고 로그도 깨끗하고 매칭 점수도 나오는데 결과만 전부 틀린다** — 실패 신호가 어디에도 없다. 지금까지 이 순서를 아는 사람이 CTO뿐이었다(#118). 아래 중 하나라도 빠지면 조용히 어긋난다.

1. **파인튜닝**(GPU 서버) — `tools/finetune/train.py` → `merge_head.py`(헤드+백본 병합). 상세 `tools/finetune/README.md`. ※ 파인튜닝 없이 다른 사전학습 모델로 교체하면 이 단계는 건너뛰고 2번부터.
2. **export + 검증** — AdaFace는 `tools/export_adaface_onnx.py`(원본↔출력 코사인 기준 미달이면 파일을 남기지 않음), R50/R100은 `merge_head.py --export-onnx`(재export 코사인 ≈1.0 재검증). **서빙은 ONNX만**(#88).
3. **모델 배치** — 새 `.onnx`를 서버 `AUTOGT_MODELS_DIR`에 둔다. **모델 파일은 볼륨이라 배포(`git pull`+compose)로 안 따라온다**(rules/06, #114). 파일명이 갤러리 `ensemble` 메타의 `model_name`으로 박히므로 파일명을 임의로 바꾸지 말 것.
4. **갤러리 재구축** ★ *가장 빠뜨리기 쉽고 가장 위험* — 보관 사진(SCR-004)에서 앙상블 임베딩 2벌을 새 모델로 다시 뽑아 `registered_faces`에 백필한다:
   ```bash
   AUTOGT_MODELS_DIR=<모델폴더> python tools/backfill_ensemble_gallery.py <등록사진루트> \
     --arcface <새 arcface.onnx> --adaface <새 adaface.onnx> --dry-run    # 먼저 dry-run으로 확인
   # 이상 없으면 --dry-run 빼고 다시 실행
   ```
   재촬영 없이 보관 사진만 있으면 된다(그래서 SCR-004 "사진도 함께 보관"이 존재). 사진이 없는 등록자는 재촬영이 필요하다.
5. **임계값 재측정** — `tools/verify_ensemble_accuracy.py <데이터셋> --enroll 10 --min-imgs 15`로 세션분리 정확도·`MATCH_THRESHOLD`를 **새 모델 기준으로** 재확인한다(폐쇄집합 착시 주의 — 1차 94.8%가 27.1%로 무효화된 전례). 필요 시 `benchmark/crossday.py`·`loso.py`.
6. **기동** — `docker compose up -d`. 기동 시 `app/services/identification.py`가 로드한 모델 지문을 로그로 찍고 갤러리 `ensemble` 메타의 모델명과 대조한다(#114·#121, #118-①). **불일치 경고가 뜨면 4번(백필)을 빠뜨린 것이다 — 그 상태의 매칭 결과는 신뢰할 수 없다.**

> - 자동 확인 현황: 기동 시 지문 로그·대조는 #114·#121로 **부분 구현**, 정확도 회귀 자동 게이트는 #115(미구현). 이 체크리스트는 그 자동화가 완성되기 전까지의 **사람용 안전 순서**다.
> - 선행: 새 모델을 제대로 **평가**하려면 등록 사진의 세션 구분(#109)이 필요하다 — 지금은 파인튜닝 결과를 평가할 조건이 아직 아니다. 다만 위 순서(특히 4·6번)는 지금도 유효하다.

#### 비전 파이프라인 — 탐지·인식 2단계 분리 (2026-08-14, 99 참조)

- 상태: ✅ 결정 (⚠ CJY 요청으로 구현, **CTO 승인 대기** — 승인 전까지 `DETECTION_STAGED` 운영 기본값 전환 보류)
- 결정: 한 사이클 안에서 이어붙이던 탐지·인식을 **DB(`detection_candidates`)를 사이에 둔 두 단계**로 끊는다.

  | 단계 | 하는 일 | 비용 성격 | 코드 |
  |---|---|---|---|
  | ① 탐지 | 프레임 → YuNet 탐지 → 5점 랜드마크로 112×112 정렬 → 확장 크롭 → **큐 적재** | CPU·프레임 속도에 묶임 | `DetectionPipeline` (staged) |
  | ② 인식 | 큐에서 꺼냄 → ArcFace-R100 + AdaFace-ir101 임베딩 → 등록부 매칭 → 쿨다운 → `detection_events` 저장 → `detection_records` 기록 → Spring 발행(API-009) | GPU·모델에 묶임 | `RecognitionWorker` |

- 이유:
  - **비용과 수명이 다르다.** 임베딩은 탐지보다 훨씬 비싸다(정렬 + ONNX 2회). 한 루프에 묶여 있으면 인식이 밀리는 순간 탐지 주기까지 함께 늘어나 **프레임을 놓친다** — AIMD가 완화하는 것이 정확히 그 증상이고, 큐는 그 원인을 없앤다
  - **재기동을 견딘다.** 지금은 서버가 죽으면 그 순간 카메라에 있던 얼굴이 함께 사라진다. 큐에 있으면 워커가 다시 떠서 이어 처리한다
  - **엣지 전환 지점과 같은 자리다.** ①의 산출물이 곧 API-019(Jetson→FastAPI 탐지 수신) 계약의 내용(bbox·랜드마크·크롭)이라, 탐지를 카메라로 옮길 때 ②는 손대지 않는다
- ⚠ **정확도는 바뀌지 않아야 한다.** 정렬 이미지를 **PNG(무손실)**로 싣는 이유가 이것이다 — JPEG로 실으면 임베딩이 미세하게 달라져 05_AI의 실측 임계값(0.40)이 잰 것과 다른 입력이 된다. 크롭(증빙용)은 사람이 보는 이미지라 JPEG로 둔다
- ⚠ 개인정보 측면의 상충과 그 방어는 `rules/04_DATABASE.md` 개인정보 보존기간 절의 `detection_candidates` 항목이 원본이다 — **작업 큐이지 기록이 아니다**
- 결정일: 2026-08-14

#### 비전 파이프라인 — 탐지 **위치**(ROI)를 관측 선택에 반영 (2026-08-19, C-2 · 99 참조)

- 상태: 📝 **설계 확정 · 미구현** (CJY 방향 제시·정정 2026-08-19). 두 기전 **모두 설정 미지정이면 현행과 완전히 동일**하다 — C-1의 `MATCH_TOPK=1`과 같은 방식
- 배경: 엘리베이터 앞처럼 **사람이 정면으로 서서 잠시 멈추는 구역**은 자세·거리·모션블러가 한꺼번에 좋다. 지금은 얼굴이 프레임 **어디에서** 잡혔든 똑같이 취급한다 — 공짜로 얻을 수 있는 신호를 안 쓰고 있고, 학습이 0인 **순수 룰베이스**다

##### 원칙 — ROI는 판정 **기준**을 바꾸지 않는다 (2026-08-19 확정)

**구역별로 임계값·margin을 따로 두지 않는다.** ROI가 정하는 것은 오직 **어느 관측을 쓸지**다.

- **근거 ① 표본이 없다.** 미등록 조회 135장에 오통과가 5건이다. 안/밖으로 쪼개면 2건 대 3건이라 구역별 임계값을 정할 근거가 성립하지 않는다. A(margin)조차 이 평가셋 과적합 경고가 붙어 있다(위 A 고도화 절)
- **근거 ② 설명 가능해야 한다.** 같은 사람이 **어디에서 잡혔느냐에 따라** 통과/불통과가 갈리면, 오알림 한 건을 추적할 때 근거를 댈 수 없다
- **근거 ③ 시간 게이트가 이미 그 일을 한다.** "수업 중 통행"처럼 판정에서 빼야 할 것은 `OUTSIDE_WINDOW`(본인 강의 퇴실창 밖)가 걸러 대시보드엔 남기고 문자로는 안 보낸다 (#141). 위치 게이트가 대신할 이유가 없다

```
프레임 → YuNet 탐지 → 정렬 →│ 임베딩(GPU) │→ 판정 → 발행 → Spring(API-009)
                        ↑                                  ↑
                     [가] 큐 순서                        [라] 보류
```

| 기전 | 자리 | 무엇을 정하나 | 설정(기본 = 현행) | 전제 |
|---|---|---|---|---|
| **가** 큐 우선순위 | GPU **앞** | 부하가 넘칠 때 **무엇을 버리나** — 임의 → ROI 밖부터 | `CAMERA_ROI` 미설정 | ⚠ `DETECTION_STAGED=true` |
| **라** 발행 보류 | GPU **뒤** | 더 나은 관측이 있을 때 **어느 것을 대표로 쓰나** | `ROI_HOLD_SECONDS=0` | 없음 |

⚠⚠ **어느 기전도 ROI 밖을 처리 대상에서 빼지 않는다.** 탐지는 **퇴실 처리가 아니라 잔존 증거**다 — `DetectionService.receive()`는 로스터를 건드리지 않고, `REMAINING`(명단 잔존) + 퇴실창 안 + 예외 없음이면 알림을 발행할 뿐이다(명단에서 지우는 것은 LMS 퇴실 태그, BAT-001). **"아직 있다"는 사실은 복도에서 잡히든 엘리베이터 앞에서 잡히든 똑같이 성립한다.** 밖 관측을 버리면 그만큼 알림이 누락된다.

- **놓침**(인식 실패) → 알림이 **안 나간다**. 미퇴실자를 놓치는 방향이고, 위 SFace 임계값 경고(*"등록자를 못 알아보는 쪽으로 실패 — 기능 목적에 직접 반한다"*)와 같은 실패다
- **오식별·오통과** → **엉뚱한 학생**에게 알림이 간다

##### 가 — 큐 우선순위 (`detection_candidates`) — ⏸ **보류** (2026-08-19)

⏸ **착수를 미룬다.** 전제가 둘인데 둘 다 아직 없다 — ① `DETECTION_STAGED=true` 승인 (`docs/pm/승인요청_DETECTION_STAGED.md`) ② **부하가 실제로 관측될 것**. 가는 "넘칠 때 무엇을 버리나"를 정하는 기능이라, 넘치지 않으면 켜 두어도 하는 일이 없다. 실측에서 큐 적체가 확인되면 그때 아래 설계대로 넣는다 — 설계는 그때 다시 짜지 않아도 되도록 남겨 둔다.

⚠ 다만 **라는 가를 전제로 이미 양방향**이다(아래). 가가 나중에 들어와도 라를 고칠 필요가 없게 해 둔 것이므로, 순서가 뒤집혀도 안전하다.


**전 카메라의 얼굴을 모아 한 번에 정렬**한 뒤 적재하고(`_detect_all`), `enqueue`가 `roi_out`을 저장하며, `claim`이 `sort=[("roi_out", 1), ("created_at", 1)]`로 꺼낸다. **ROI 밖 얼굴도 결국 전부 꺼내진다** — 순서만 바뀐다.

- **근거는 부하다.** 사이클 1.0초 / 과부하 판정선 80% = 예산 800ms, 앙상블 임베딩 167ms/얼굴 → **사이클당 약 4.8명**이 한계다. 카메라 3대에 2명씩만 있어도 초과하고, 하필 **수업 종료 직후**가 그 시간대다
- ⚠ **`HIGH_LOAD_RATIO`를 올려도 해결되지 않는다.** AIMD 간격의 상한이 시작값(`DETECTION_INTERVAL_SECONDS`)과 같아 과부하에서 `min()`에 막힌다 — 판정선은 "얼마나 빨리 물러날까"이지 처리량 손잡이가 아니다. 부하를 실제로 푸는 건 셋뿐이다: **보낼 얼굴을 줄이거나(가) · 탐지를 인식에서 떼거나(2단계) · 얼굴당 비용을 줄이거나(배치 추론·GPU)**

**정렬은 카메라 안이 아니라 전역이어야 한다.** 지금 `_detect_all`은 용량(`remaining_capacity`)을 사이클당 한 번 재서 **전 카메라가 공유**하는데 소비는 카메라 순서대로다 — 카메라1이 ROI 밖 얼굴로 용량을 다 쓰면 **카메라2의 ROI 안 얼굴이 아예 못 들어간다.** 그래서 ① 전 카메라 탐지·수집 → ② 전역 정렬 후 적재의 2단계로 바꾼다.

**두 정렬은 하는 일이 다르다.**

| 정렬 | 하는 일 |
|---|---|
| 적재 정렬 (`_detect_all`) | 용량이 모자랄 때 **무엇을 버릴지** 고른다 |
| `claim` 정렬 | **처리 순서**를 정한다 |

여유가 있을 때는 적재 정렬이 사실상 무효다(전부 실리고 순서는 `claim`이 정한다). **적재 정렬은 용량이 모자랄 때만 의미가 있다** — 가가 부하 상황을 위한 장치라는 것이 여기서 그대로 드러난다.

**필드가 `in_roi`가 아니라 `roi_out`(참 = 밖)인 이유.** Mongo 정렬은 `null < false < true`다. 필드가 없는 **구버전 문서가 null**이 되므로:

| 정렬 | 순서 | 판정 |
|---|---|---|
| `in_roi` 오름차순 | 구버전 → **밖** → 안 | ❌ 우선순위가 뒤집힌다 |
| `in_roi` 내림차순 | 안 → 밖 → **구버전** | 배포 순간 큐가 밀려 있으면 구버전이 뒤로 밀려 **TTL 15분에 조용히 사라진다** (그 얼굴은 영영 인식되지 않는다) |
| **`roi_out` 오름차순** | **구버전 → 안 → 밖** | ✅ 우선순위도 맞고 구버전도 안 굶는다 |

- **ROI 미설정 카메라는 `roi_out=false`**(= ROI 안과 같은 우선순위)로 둔다. 운영에서는 **모든 카메라에 ROI를 지정할 예정**이라 이 규칙이 쓰일 일이 없지만, **폴리곤 파싱 실패·신규 카메라 추가 직후**의 안전 방향으로 남긴다 — 설정이 없다는 이유로 그 카메라를 굶기면 안 된다
- **ROI 판정은 서버가 한다 — 젯슨에 두지 않는다.** ① 폴리곤은 카메라 각도에 묶이고 각도는 바뀌므로, 서버 `.env` 한 줄이면 될 일을 현장 기기마다 배포·재기동하게 된다 ② API-019 계약이 이미 bbox를 담고 있어 **계약을 안 바꿔도 된다**(펌웨어 버전과 정책 버전이 독립으로 움직인다) ③ 젯슨이 낡은 폴리곤을 들고 있어도 서버는 알 방법이 없다 ④ 큐 자체가 서버에 있다. ⚠ 나중에 정책이 "ROI 밖은 아예 안 보낸다"로 바뀌면 **그때는 젯슨이 맞다** — 지금은 배제하지 않으므로 어차피 다 보내야 한다
- 복합 인덱스 교체가 따라온다(`{status, created_at}` → `{status, roi_out, created_at}`). `02_indexes.js`의 `DROPPED` 목록에 옛 인덱스를 넣고 → `database/apply.sh` 재적용. `remaining_capacity`의 `count_documents({status:"pending"})`은 새 복합의 **접두**라 그대로 커버된다
- ⚠ **이미 가득 찬 큐는 가가 못 고친다.** 새로 잡힌 ROI 안 얼굴이 와도 큐가 밖 문서로 가득하면 그냥 버려진다(밀어내기는 넣지 않는다). 상한 500 × 167ms = **83초치 적체**라, 거기 닿았다면 이미 다른 것이 잘못된 상태다
- ⚠ **정렬은 로그가 없으면 일하는지 알 수 없는 종류의 변경이다.** `status_snapshot`에 ROI 밖 적재·폐기 카운터를 내고, `_warn_queue_full` 로그에 "버린 n건 중 밖 m건"을 붙인다

##### 라 — 발행 보류 (`EventEmitter.emit`)

```
ROI 안 → 즉시 발행 + 임베딩을 창 길이만큼 "최근 발행" 기억에 남긴다
         + 버퍼에 닮은 보류분이 있으면 취소
ROI 밖 → 최근 발행 기억에 닮은 것이 있으면 → 발행하지 않고 버린다
         없으면 → 버퍼에 보류
버퍼 만료(창) → 발행          ← 배제하지 않는다
```

- **"같은 사람"은 `student_id`가 아니라 임베딩 코사인으로 본다.** `student_id`로 묶으면 밖에서 **B로 오식별**된 건이 안의 A와 서로를 못 알아봐, 정작 잡으려던 케이스에서 작동하지 않는다. 임베딩은 이미 계산돼 있어 **추가 추론이 0**이고, 버퍼 10건이면 512차원 내적 10회다
- ⚠⚠ **"최근 발행 기억"이 없으면 가가 라를 무력화한다.** 가는 ROI 안을 먼저 처리하므로 **밖 관측이 항상 나중에** 나온다. 라가 "밖을 보류했다가 안이 오면 취소"만 한다면, 안이 이미 발행된 뒤에 밖이 도착해 **취소할 대상이 없고 창 만료 후 오식별이 그대로 나간다.** 하필 **둘 다 중요해지는 순간(부하)에 서로를 방해한다** — 모든 카메라에 ROI를 지정하면 가가 상시 작동하므로 이 역전도 상시화된다. 그래서 라는 **양방향**이어야 한다: 밖→안(보류 취소)과 안→밖(발행 억제)을 모두 덮는다
- ⚠ **대조 기준 시각은 `detected_at`이다 — 처리 시각이 아니다.** "같은 사람의 같은 방문인가"는 **사람의 동선 시간**이지 큐가 얼마나 밀렸는지가 아니다. 부하 상태에서 가가 작동하면 안과 밖의 **처리** 시각 간격이 수십 초까지 벌어지는데 **탐지** 시각 간격은 1초다 — 처리 시각으로 재면 창을 넘겨 대조에 실패한다. `detected_at` 기준이면 창 값도 2단계에서 재는 **밖→안 전이 시간 p90** 하나로 통일된다
- ⚠⚠ **시계가 둘 공존한다. 구현할 때 섞지 말 것.** 기존 쿨다운은 **발행 시각(monotonic)** 기준이고 그건 의도된 것이다(`EventEmitter.emit` 주석 — 목적이 "알림이 도배되지 않게"라 나가는 쪽 시계가 맞다). 라의 임베딩 대조만 `detected_at`을 쓴다. 메모리 상한을 위한 기억 항목 **퇴출**과 보류 만료는 **경과 시간(`monotonic`)**으로 재되 넉넉히 잡는다 — 벽시계(`datetime.now()`)는 NTP·서머타임으로 뒤로 점프할 수 있어, 경과 시간을 재는 자리에 쓰면 보류가 영영 안 끝나거나 즉시 만료된다
- 사실상 **임베딩 기반 쿨다운**을 하나 더 두는 것이다. 지금 쿨다운은 `(camera_id, student_id)` 키라 오식별일 때 걸리지 않는데, 그것이 정확히 라가 잡으려는 케이스다
- **지연 비용이 사실상 없다.** 미퇴실 알림은 탐지 즉시가 아니라 강의별 `T_out−60분` 배치(BAT-003, specs/12)로 나간다 — 발행이 몇 초 늦어도 그 배치 시점에 반영돼 있으면 결과가 같다
- ⚠ **마감 임박 flush 필요** — 탐지가 `T_out−60분` 직전에 걸리면 보류분이 배치를 놓치고, `batch_runs` 성공 이력 때문에 재확정되지 않아 복구되지 않는다
- ⚠ **보류분·기억은 메모리라 프로세스가 죽으면 창 길이만큼 유실**된다. 창이 짧아야 하는 이유다
- ⚠ **인라인 경로는 크롭만 들고 보류할 것.** 지금 `_handle`의 `record` 클로저가 **원본 프레임을 통째로 캡처**한다 — 그대로 보류하면 건당 ~900KB가 물린다. 2단계가 쓰는 `record_crop` 경로로 갈라 수십 KB로 떨어뜨린다
- **왜 GPU 뒤인가 — "GPU로 보낼 사진을 고르는 데" 쓰지 않은 이유** (반복해서 나오는 질문):
  - ① **GPU 앞에서는 "같은 사람"을 알 수 없다.** 보류의 목적이 *더 나은 관측으로 갈아끼우기*인데, 신원은 **임베딩에서 나오고 임베딩이 곧 GPU**다. 앞에는 bbox·정렬 이미지뿐이라 물을 수단이 없다. 트래커로 우회하려 해도 "복도 → 엘리베이터 앞"처럼 **탐지가 끊겼다 이어지는** 구간은 IOU로 못 잇는다(트랙 단위 판정을 접은 이유와 같다)
  - ② **개인정보 근거가 무너진다.** 앞에서 보류하려면 정렬 이미지를 창 길이만큼 `detection_candidates`에 붙들어야 하는데, 그 컬렉션은 **아직 누구인지 모르는 얼굴**이 담긴 곳이라 "처리 즉시 삭제가 정상 경로"다(rules/04). 일부러 오래 두면 2단계 분리의 방어가 통째로 무너지고 상한 500건도 더 빨리 찬다. 뒤에서 붙드는 것은 임베딩·판정 결과(건당 ~4KB)이고 이미 신원을 아는 상태다
  - ③ **부하 기전이 아니다.** 라는 버리는 것이 아니라 대표를 고르는 것이고, 창이 지나면 밖 관측도 그대로 발행해야 하며 그러려면 `student_id`가 있어야 한다 — **어차피 전부 GPU를 탄다.** 부하는 가가 맡는다(가=GPU 앞·부하, 라=GPU 뒤·정확도). 한 자리에 합치면 서로의 목적을 망친다
  - ④ **발행은 되돌릴 수 없다.** API-009로 나가면 Spring이 저장하고 알림까지 발행하며 **취소 API가 없다.** 그래서 보류가 앉을 자리는 **누구인지 알게 된 직후 · 되돌릴 수 없게 되기 직전** 하나뿐이고, 그 이음매가 `EventEmitter.emit`이다
- **이 기전은 "트랙 단위 판정"(사람이 프레임에서 사라질 때 관측을 모아 판정)의 경량 대안이다.** 트랙 판정은 지연이 **체류 시간**이라 통제할 수 없고 트래커가 신규다. 라는 지연을 **우리가 정하고**(창) 이미 있는 임베딩을 재사용한다

##### ROI 구역은 어떻게 확정하나 — **통과 필연성이 필요조건, 품질이 목적함수**

ROI는 "화질이 제일 좋은 칸"이 아니라 **엘리베이터를 타려면 얼굴이 반드시 지나가는 구역**이다 (2026-08-19 CJY 정정). 품질만 보고 좁게 그리면 그 칸을 비껴간 사람이 통째로 빠지는데, **두 기전 모두 "ROI 관측이 있다"를 전제로 동작하므로 빠진 사람에게는 아무것도 해 주지 못한다.**

| | 조건 | 근거 자료 |
|---|---|---|
| **필요조건** | 엘리베이터를 탄 사람 중 ROI 안에서 **최소 1회** 잡힌 비율 ≈ 100% | 얼굴 bbox 중심 **점유(occupancy) 히트맵** |
| **목적함수** | 그 조건을 만족하는 영역 중 **매칭 성공률 최대** | 칸별 **성공률 히트맵** |

→ **통과율 100%를 만족하는 가장 작은 영역.** 넓힐수록 통과율↑·품질 이점↓이라 폴리곤 크기가 그대로 손잡이다.

1. 영상을 **유도용 / 검증용으로 가른다** — 같은 영상 안에서 나누면 연속 프레임의 같은 사람이 양쪽에 걸쳐 새어 나간다
2. 유도용 영상에서 **점유 히트맵**과 **성공률 히트맵**을 함께 쌓는다
3. 점유가 사실상 전원인 칸으로 최소 영역을 잡고 → 이진화 → `findContours` → `approxPolyDP` → 폴리곤
4. **검증용 영상**으로 **통과율**과 안/밖 성공률 격차를 함께 본다 — 통과율이 안 나오면 **폴리곤이 좁은 것**이고, 격차가 없으면 **자리가 틀린 것**이다

- 좌표는 **정규화 폴리곤**이라 해상도가 바뀌어도 유효하다. 카메라별 설정(`CAMERA_ROI`), 미설정 카메라는 ROI 개념 자체가 꺼진다
- **모든 카메라에 ROI를 지정한다** (2026-08-19 확정). 각 카메라의 ROI는 **그 카메라 시야에서의 목**이다 — 12층 엘리베이터 카메라는 엘리베이터 앞, 1층 카메라는 출입문으로 서로 다른 지점이다. 따라서 **유도·검증을 카메라 수만큼 반복**하고, 도구도 카메라별로 도는 구조로 만든다. 카메라마다 **실제 설치 각도의 영상**이 있어야 최종 폴리곤이 나온다
- ⚠ **폴리곤은 카메라 각도에 묶인다.** 카메라를 돌리거나 옮기면 무효가 되는데 **에러가 나지 않는다** — 조용히 틀린다. 설치 각도 확정 후 재확인이 필요하다
- ⚠ **YuNet에는 ROI 파라미터가 없다**(`setInputSize`·`setScoreThreshold`·`setNMSThreshold`·`setTopK`뿐). 프레임을 잘라 탐지하면 경계에 걸친 얼굴이 잘리고, 좌표 오프셋 복원을 빠뜨리면 정렬이 통째로 틀어진다 — **전체 프레임 탐지 후 bbox 중심으로 필터**한다. 목적이 "탐지 제한"이 아니라 "GPU로 보낼 것 고르기"이고, 비싼 건 탐지(9.4ms)가 아니라 임베딩(167ms)이라 절감 효과는 그대로다

##### ⚠ 이 설계가 못 돕는 케이스 (알고 받아들인다)

복도에서는 **옆모습만** 나오다가 엘리베이터 앞에서 **고개를 숙인 채**(휴대폰) 탑승하는 흐름이면, ROI 안에 쓸 만한 관측이 아예 생기지 않는다 — 고개를 숙이면 YuNet이 못 잡거나 잡아도 랜드마크가 퇴화해 정렬 단계에서 버려진다. 이 사람은 **ROI 밖 데이터만으로 판정된다.**

- 라는 이때 **지연만 만들고 결과를 못 바꾼다**(창 만료 후 밖 관측 그대로 발행). 정상 동작이다
- 구역별 기준을 두어 구제하려는 시도가 위 "원칙"에서 기각된 그것이다 — **어쩔 수 없는 케이스로 받아들인다**
- 이 비율이 곧 **C-2 설계의 상한**이다. `recover_probe_bbox` 산출물의 "밖에서만 잡히는 사람 비율"이 그 값이므로, 실측 후 문서에 적을 것

##### 선행 작업 — `tools/recover_probe_bbox.py`

평가셋이 **얼굴 크롭 파일 모음**이라 프레임 좌표도 시간축도 없다. 크롭을 원본 영상으로 되돌려야 아래가 정해진다.

| 산출 | 정하는 것 |
|---|---|
| 점유 히트맵 → 통과율 | 폴리곤의 **필요조건** 충족 여부 |
| 안/밖 성공률 격차 | 폴리곤 자리 검증 + 라의 전제("안이 밖보다 낫다") |
| 밖→안 전이 시간 분포(p90) | 라의 보류 창 |
| 밖에서만 잡히는 사람 비율 | 위 "못 돕는 케이스"의 크기. **그 여집합이 설계 상한**이고, 더 좁게는 "안+밖" 방문만이 라가 결과를 바꿀 수 있는 몫이다 |

⚠ **복원 가능 여부가 미검증이다.** 크롭 파일명이 원본 프레임을 지목하지 못하면 여기서 막히고 방법이 바뀐다 — 그래서 **파일명 규칙 확인이 첫 작업**이다

⚠ **C-2는 specs/16 §5 비교표에 숫자를 못 낸다.** 두 기전 모두 판정 기준을 안 바꾸므로 4지표가 움직이지 않는다(평가 도구에는 큐도 시간축도 없다). C는 **C-1(top-k)로 겨루고**, C-2의 산출물은 위 표의 대조·분포다.

  - 기본값을 `test`로 두는 것이 핵심이다 — 설정을 잊었을 때 안전한 쪽으로 실패해야 한다
  - **학번 매핑 (2026-08-14 추가)**: `SMS_TEST_RECIPIENT`는 두 형식을 받는다.
    | 형식 | 예 | 수신자 |
    |---|---|---|
    | 번호만 | `010-1111-1111,010-2222-2222` | 누가 탐지되든 **적힌 전원** |

    - 왜 필요한가: 번호만 적으면 누가 탐지되든 같은 문자가 전원에게 가서 **문자만 봐서는 누구를 탐지했는지 알 수 없다.** 얼굴 등록자와 번호를 묶으면 **`SMS_MODE=test`를 유지한 채로** "그 사람에게만 갔는가"까지 검증된다 — live로 바꾸지 않으므로 실제 학생에게 나갈 위험은 그대로 0이다
    - ⚠ **`daily_roster.phone`에 손으로 넣는 방법은 안 된다** — BAT-001이 1분마다 명단을 upsert하면서 LMS 응답에 없는 연락처를 **null로 덮어쓴다**(`DailyRosterPersistenceAdapter`). 넣어둬도 다음 tick에 사라진다
    - ⚠ **매핑에 없는 학번은 아무에게도 보내지 않는다** (전원 발송으로 되돌아가지 않는다). 되돌아가면 실제 학생이 탐지될 때마다 팀원 전원이 문자를 받고, 구분하려던 목적도 사라진다. `detection_alerts`에 FAILED로 남아 화면에서 보인다
    - 기동 로그가 어느 형식으로 읽혔는지 알려준다 — `SMS_MODE=test — 학번 매핑 N명, …`
- **발송 직전 최종 확인 (2026-08-07 추가)**: 카메라 포착으로 발송 대상이 확정돼도, **문자를 보내기 직전에 LMS를 1회 재조회해 퇴실 여부를 최종 확인**한 뒤 발송한다. 폴링 주기(최대 1분) 사이에 정상 퇴실 태그가 찍힌 사람에게 복귀 문자가 나가는 오발송을 원천 차단하기 위함 — 실측상 정상 퇴실 태그가 수업 종료 이후에도 계속 찍힌다(specs/12 BAT-001 실측). 문자는 하루 몇 건이라 호출 부담이 없고, 이 장치 덕에 폴링 주기를 완화해도 안전하다

  학생 프로젝트가 쓰는" 문제가 사라진다 — **우리 솔라피 계정에 학원 채널을 연결**하고 문자 발송에 쓰던
  계정·코드를 그대로 재사용하는 그림이다
  - ⬜ **미검증** — 실제 연결 신청·승인을 해 봐야 확정된다. 대행사·채널 정책에 따라 추가 요건이
    나올 수 있다. **연결 테스트 후 이 절을 실제 절차로 갱신할 것** (아래 "검증 대기" 표 참조)

#### ⬜ 검증 대기 — 연결·테스트 후 갱신할 항목 (2026-08-11 기준)

이 절에서 **아직 실물로 확인하지 않은 것**만 모아 둔다. 나머지(채널 메시지 배제·비용·관문 구조·
test 모드 규칙)는 공식 문서와 우리 데이터로 확인을 마쳤다.

| 항목 | 현재 서술 | 검증 방법 |
|---|---|---|
| 우리 솔라피 계정 ↔ 학원 채널 연결 | 가능할 것으로 본다 | 솔라피 콘솔에서 신청 → 관리자센터 승인까지 실행 |
| 템플릿 초안의 심사 통과 | 정보성이라 통과 가능성이 높다 | 실제 신청 후 승인/반려 확인 |
| 승인 템플릿의 변수명 | `#{시각}` 1개로 설계 | 승인본 확인 (심사 중 문구 수정 시 변경됨) |
| 알림톡 단가 | 통상 문자보다 저렴 | 계약 시 실단가 확인 |
- ❌ 안 푼 것: **아직 알림톡을 보낼 수 있는 상태가 아니다.** ③ 발신프로필과 ④ 템플릿 승인이 남았고,
  ④는 여전히 영업일 1~3일이 걸리는 임계경로다

#### ⚠ 안전: test 모드에서는 알림톡을 쓰지 않는다 (2026-08-11 확정)

`SMS_MODE=test`일 때는 **알림톡을 시도하지 않고 기존 문자 경로로 보낸다.** 이유 둘 다 되돌릴 수 없는 쪽이다:

1. **승인된 템플릿은 본문을 변조할 수 없다** — test 모드의 표식인 `[TEST]` 접두어를 붙일 방법이 없어,
   테스트 발송과 실발송이 수신자에게 똑같이 보인다
2. **학원 채널 이름으로 나간다** — 문자는 발신번호만 보이지만 알림톡은 학원 브랜드가 찍힌다.
   테스트 메시지가 학원 이름으로 나가는 사고는 우리 쪽 실수로 끝나지 않는다

→ 구현 시 규칙: **알림톡 사용 조건 = `SMS_MODE=live` AND `pfId`·`templateId` 설정됨.**
   둘 중 하나라도 없으면 조용히 문자로 보낸다(발송 자체를 막지는 않는다 — 메시지는 도달해야 한다).

#### 대행사는 반드시 거친다 — 단, 솔라피일 필요는 없다 (2026-08-11 추가)

카카오는 **알림톡 API를 개별 사업자에게 직접 열어주지 않는다.** 발신프로필도 채널 관리자센터에서 혼자
만드는 것이 아니라 **대행사 시스템에서 채널+사업자번호를 연결해 발급**받는다. 즉 "대행사 없이 직접"은
선택지가 아니고, **어느 대행사냐**만 고르는 문제다 (솔라피·NHN Cloud·네이버 SENS·알리고·비즈엠·인포뱅크 등).
지금 솔라피를 쓰는 것은 **문자 때문**이지 알림톡 때문이 아니다 (SENS는 사업자 계정만 가입 가능해 배제 —
2026-08-09 경위).

| 경로 | 장점 | 단점 |
|---|---|---|
| **학원의 기존 대행사 재사용** (권장) | 발신프로필·**승인 템플릿을 이미 가진 자산으로 재사용** → 심사 대기(1~3영업일)를 건너뛸 수 있다 | 학원 계정 자격증명을 받아야 하고, 대행사가 솔라피가 아니면 발송 스크립트 재작성 |
| 솔라피에 별도 발신프로필 | 우리 계정이라 테스트가 자유롭다 | 사업자 인증을 학원에 다시 요청 + 템플릿 심사도 새로 |

- 같은 채널이라도 **대행사별로 발신프로필을 따로 발급**받을 수 있어 둘 다 가능하다. 다만 8/31까지
  영업일이 얼마 없어 **기존 자산 재사용이 압도적으로 유리**하다
- 이 선택은 회의 결정과도 맞는다 — **"실배포 시 학원 전용 발송 서비스로 연동"**(2026-08-11 확정)의
  자리가 곧 학원 대행사 자리다
- ⚠ **③이 일정의 임계경로다** — 심사 반려 시 수정·재신청으로 다시 1~3일. 최종발표(8/31) 역산하면
  **템플릿 신청을 먼저 올려두고 코드를 나중에 붙이는 순서**가 안전하다
- 승인된 템플릿은 **본문을 임의로 못 바꾼다** (변수 자리만 치환) — 문구 확정이 곧 계약이다

#### 비용 — 무료 티어는 없지만 우리에겐 쟁점이 아니다 (2026-08-11)

알림톡은 카카오가 건당 과금하고 대행사가 마진을 붙이는 구조라 **무료 티어가 없다.** 그러나 우리
발송량이 극히 적어 금액 자체가 의사결정 변수가 되지 못한다.

- 문자가 나가는 조건이 **"퇴실 미체크 AND 카메라 포착"** 이중이라 대상이 하루 0~수 명이다
- 8/31까지 영업일 ≈15일 × 하루 최대 5건 = **넉넉히 75건**. 단문 문자 단가 18원 기준으로도 1,500원 미만이고,
  **알림톡은 통상 문자보다 저렴**하다
- 개발·시연 중에는 `SMS_MODE=test`라 실제 발송은 팀원 번호 몇 건뿐이다

**진짜 무료 경로는 "학원 계정에 얹는 것"이다** — 학원이 이미 알림톡을 쓰고 있다면 우리 팀 추가 비용은
0원이고, 사업자등록증 문제도 동시에 풀린다. 위 "학원의 기존 대행사 재사용" 경로가 **일정도 빠르고
비용도 0**인 이유다.

**사업자 없이 무료로 쓸 수 있는 카카오 API는 사실상 없다** — "나에게 보내기"는 무료·사업자 불필요지만
**본인 계정에만** 전송된다. "친구에게 보내기"는 학생마다 카카오 로그인·동의와 별도 권한 심사가 필요해
출결 시스템에 맞지 않는다. 시연 화면용 흉내는 가능하나 채택하지 않는다.

무료 대안 채널(Slack·이메일·디스코드)은 **즉시성 또는 수신율**에서 맞지 않는다 — Slack은 이미 행정실
알림으로 쓰고 있고(BAT-002), 학생 개인 알림에는 부적합하다.

##### 🗑 배제: 카카오톡 "채널 메시지"(친구톡 계열) — 2026-08-11 검토

대행사 없이 채널 파트너센터에서 직접 보낼 수 있어 후보로 검토했으나 **배제한다**
(근거: 카카오비즈니스 공식 문서 `channel/run/message` 확인).

| 항목 | 채널 메시지 | 우리 요구 |
|---|---|---|
| 발송 대상 | **채널을 친구 추가한 사람만** | 대상 전원에게 도달해야 함 |
| 발송 방식 | **파트너센터에서 관리자가 수동 발송** | **카메라 포착 → 즉시 자동 발송** |
| 성격 | 광고·마케팅 (카탈로그·캐러셀·퀴즈 등 9종) | 정보성 알림 |
| 단가 | 일반 15원 / 타겟 20원 (VAT 별도), 무료 건수 없음 | — |

- **결정타는 자동화 불가다.** 사람이 눌러야 나가면 이 시스템을 만든 이유가 사라진다.
  (문서의 "고객파일 API"는 발송 대상 명단 업로드용이지 발송 트리거가 아니다)
- 친구 추가를 안 한 학생에게는 아예 도달하지 않는다 — 알림톡은 전화번호 기반이라 이 제약이 없다
- 단가도 우리가 쓰는 단문 문자(18원)와 비슷하거나 비싸다. **"무료 경로"가 아니다**
- 친구톡을 API로 보내려면 결국 발신프로필이 필요하다 — "대행사 불필요"는 수동 발송에 한정된다

#### 템플릿 초안 (심사 신청용)

```
[우리인재개발원] 퇴실 미체크 안내

#{시각} 기준 퇴실 처리가 확인되지 않았습니다.
학원으로 복귀하셔서 퇴실 태그를 찍어 주시기 바랍니다.

※ 이미 퇴실하셨다면 행정실로 문의해 주세요.
```

- **정보성 메시지**라 심사 요건에 맞는다 (광고성 문구·채널 추가 유도·이모티콘 없음)
- **이름·강의명을 넣지 않는 기존 결정이 여기서 이점이 된다** — 변수가 `#{시각}` 하나뿐이라 심사가 단순하고,
  잠금화면 미리보기로 이름이 새는 위험도 그대로 차단된다 (rules/04)
- **대체발송(문자) 본문은 기존 문구를 그대로 쓴다** — 알림톡은 1,000자까지 되지만 문자는 EUC-KR 90바이트가
  한도라, 위 본문을 그대로 문자로 보내면 장문(LMS)이 되어 단가가 오른다 (18원 → 45원)

#### 코드 변경 범위 (승인 후)

- `RPAs/send_return_request.py` — **대행사가 솔라피면** payload의 `message`에 `kakaoOptions`
  (`pfId`·`templateId`·`variables`)를 추가하는 정도로 끝난다(같은 엔드포인트 `/messages/v4/send`가
  알림톡을 지원). **다른 대행사면 이 파일만 재작성** — 엔드포인트와 인증 방식(솔라피는 HMAC 서명,
  타사는 API 키 헤더 등)이 다르다. 어느 쪽이든 이 한 파일에 갇힌다
- `.env` — `KAKAO_PF_ID`·`KAKAO_TEMPLATE_ID` 추가 (`.env.example` 갱신 필수)
- `RpaSmsPort`/`RpaSmsAdapter`는 **인터페이스 변경 없음** — 채널이 늘어도 호출부는 그대로다.
  다만 이름이 SMS에 묶여 있어 전환 시 `NotificationSendPort` 등으로 개명 검토
- `SMS_MODE` 안전장치는 **그대로 유지**한다 — 채널이 바뀌어도 `test`에서 실제 학생에게 나가면 안 된다

#### 발송 채널 교체 절차 — 발표 시점 구현 범위와 인계 (2026-08-11 확정)

**프로젝트 기간(~8/31) 안에 알림톡 승인이 나지 않아도 문제가 되지 않도록 구조를 잡는다.**
발표는 **문자 발송으로 완결된 시스템**을 보여주고, 알림톡은 **교체 지점이 준비된 상태**로 인계한다.
채널이 늦어지는 것과 시스템이 미완성인 것은 다르다 — 이 구분이 서게 문서로 남긴다.

**교체 시 바뀌는 것 / 안 바뀌는 것**

| 바뀐다 | 안 바뀐다 |
|---|---|
| `RPAs/send_return_request.py` (엔드포인트·인증·payload) | 판정 로직 전체 — 카메라 포착 → roster 잔존 → 예외 확인 |
| `.env` 2줄 (`KAKAO_PF_ID`·`KAKAO_TEMPLATE_ID`) | **발송 직전 LMS 재조회**(오발송 최종 방어) |
| — | `SMS_MODE` 안전장치 (test 기본값·수신자 강제 치환) |
| — | 중복 발송 방지(`alreadySentToday`)·재시도 정책 |
| — | `detection_alerts.sms_status`·`notifications` 이력 기록 |
| — | 알람 화면(API-004)·대시보드 — 화면은 채널을 모른다 |
| — | `RpaSmsPort` 인터페이스 (교체 지점 그 자체) |

- **핵심: 안전장치와 판정이 채널 바깥에 있다.** 채널을 바꿔도 "누구에게 보낼지"를 정하는 로직과
  "잘못 보내지 않게 하는" 장치는 손대지 않는다. 이것이 포트-어댑터로 나눈 실익이다
- ⚠ **딱 하나 채널에 딸린 안전 규칙**: `SMS_MODE=test`에서는 알림톡을 쓰지 않는다(위 절) —
  승인 템플릿에 `[TEST]`를 붙일 수 없고 학원 브랜드로 나가기 때문이다

**인계 시 체크리스트** (학원 또는 후임자가 실제로 교체할 때)

1. 대행사에서 발신프로필(`pfId`)·승인 템플릿(`templateId`) 확보
2. `.env`에 두 값 추가 (`.env.example` 참조)
3. `send_return_request.py`에 `kakaoOptions` 추가 — 대행사가 솔라피가 아니면 이 파일만 재작성
4. **대체발송(문자) 본문은 기존 문구 유지** — EUC-KR 90바이트, 넘기면 장문 45원
5. `SMS_MODE=live` 전환은 별도 조건 2가지 충족 후 (연락처 확인 + CTO 승인)
6. 실발송 1건으로 `detection_alerts.sms_status`가 `SENT`로 남는지 확인 —
   **접수 성공 ≠ 발송 성공**이므로 대조 폴링 결과까지 본다 (specs/13 2026-08-09 포스트모템)

**개명하지 않는 이유** — `RpaSmsPort`·`SmsSendResult`·`sms_status`에 `Sms`가 남아 있지만 바꾸지 않는다.
`sms_status`가 DB·API-004 응답·프론트 화면까지 이어져 있어 파급이 이름값보다 크다. 의미는
**"발송 채널"**로 읽고, 포트 javadoc에 그 뜻을 적어 두었다.

#### 학원에 요청할 것 (CTO — 2026-08-12)

1. **알림톡을 이미 보내고 계신지** — 보내신다면 **승인된 템플릿을 재사용**해 심사 대기를 건너뛸 수 있는지
   (재사용 가능하면 최단 경로다). 이때 대행사가 어디인지도 함께 확인
2. 안 보내신다면 → **우리 솔라피 계정으로 채널 연결을 진행**한다. 관리자 권한이 있으니 CTO가 승인 가능
3. 어느 쪽이든 → **템플릿 심사 신청을 먼저 올린다** (임계경로 — 코드보다 앞선다)

#### 진행 순서 (역순으로 하면 손해다)
