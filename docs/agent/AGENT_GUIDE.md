# AGENT_GUIDE — AI 에이전트 작업 지침서 (하네스 진입점)

> **이 문서는 사람이 아니라 AI 에이전트가 읽는 문서입니다.**
> 이 폴더(`docs/agent/`)를 발견한 AI는 코드를 작성하기 전에 반드시 이 지침을 따른다.
> 초기 구성을 시작하는 프롬프트는 `META_PROMPT.md`에 있다.
> **특정 AI 도구에 종속되지 않는다.** Claude·Gemini·ChatGPT·Cursor·Copilot 등 어떤 AI든 이 문서를 읽으면 같은 방식으로 동작해야 한다 (0장).

## 사용 방법 (사람용 안내)

1. 새 프로젝트 리포에 이 `docs/agent/` 폴더를 통째로 복사한다.
2. 업무정의서(PRD·의뢰서·기획서 등)를 `docs/` 아래에 둔다. (예: `docs/업무정의서.md`)
3. `META_PROMPT.md`의 **[A] 초기 구성 프롬프트**를 복사해 경로만 바꿔 AI에게 붙여넣는다.
4. AI가 업무정의서로 채우고 남은 항목만 질문한다. 답하면 하네스 파일이 생성되고 개발이 시작된다.
5. 파일을 직접 읽지 못하는 채팅형 AI(웹 ChatGPT·Gemini 등)라면 이 문서와 업무정의서를 첨부하거나 붙여넣는다.

## 0. 에이전트 호환 규칙 (어떤 AI에서도 동작)

### 0-1. 도구 중립 원칙
- 규칙의 원본은 `docs/agent/`의 마크다운뿐이다. 특정 도구 전용 문법(`@파일` 참조, 슬래시 명령, 특정 MCP·스킬 이름)에 의존하는 규칙을 쓰지 않는다. 파일은 **리포 루트 기준 경로**로 지칭한다.
- 도구 전용 기능(MCP, 스킬, 훅, 서브에이전트)은 **있으면 쓰는 보조 수단**이다. 없어도 같은 결과를 내는 수동 절차가 문서에 있어야 한다.
- 이 문서의 "AI"는 사용 중인 모든 에이전트를 가리킨다.

### 0-2. 능력 수준별 동작
AI는 작업을 시작할 때 자기 능력 수준을 판단하고, 그 수준에 맞게 동작한다.

| 수준 | 예 | 파일 | 명령 실행 | 동작 방식 |
|---|---|---|---|---|
| L3 에이전트형 | Claude Code, Gemini CLI, Codex CLI, Antigravity, Cursor·Windsurf 에이전트 | 읽기·쓰기 | 가능 | 문서대로 전부 직접 수행 (구현·서버 기동·E2E·커밋) |
| L2 편집형 | IDE 채팅(Copilot Chat 등) — 실행 불가 설정 | 읽기·쓰기 | 불가 | 파일은 직접 고치고, 실행·검증·커밋 **명령을 출력**해 사용자에게 실행을 요청한 뒤 결과를 받아 이어간다 |
| L1 채팅형 | 웹 ChatGPT·Gemini·Claude.ai | 첨부·붙여넣기만 | 불가 | 바꿀 파일마다 **경로 + 전체 내용**(또는 명확한 diff)을 출력하고, 실행할 명령을 순서대로 제시한다. 필요한 파일이 첨부되지 않았으면 추측하지 말고 요청한다 |

- L1·L2는 검증을 직접 못 했으므로 보고에 **"미검증 — 사용자 실행 필요"**로 표시하고, 사용자가 붙여준 실행 결과로 다음 단계를 판단한다.
- 커밋도 수준에 따른다: L3는 직접 커밋, L1·L2는 업무 묶음이 끝날 때마다 `git add …` / `git commit -m "…"` 명령을 출력한다 (rules/08).

### 0-3. 진입점 파일
도구마다 자동으로 읽는 파일이 달라서, **`AGENTS.md`를 표준 진입점**으로 두고 다른 파일은 그쪽을 가리키게 한다. 템플릿은 `ENTRY_TEMPLATE.md`.

| 도구 | 자동으로 읽는 파일 | 내용 |
|---|---|---|
| 공통 표준 (Codex, Cursor, Copilot 에이전트 등) | `AGENTS.md` | **본문** — 핵심 규칙 요약 + docs/agent 안내 |
| Claude Code | `CLAUDE.md` | 포인터 (`@AGENTS.md` 임포트 + 안내 한 줄) |
| Gemini CLI | `GEMINI.md` | 포인터 |
| Antigravity | `.agents/rules/*.md` | 포인터 |
| Cursor | `.cursor/rules/*.mdc` | 포인터 (AGENTS.md를 직접 읽으면 생략) |
| Windsurf | `.windsurfrules` | 포인터 |
| GitHub Copilot | `.github/copilot-instructions.md` | 포인터 |
| 채팅형 (L1) | 없음 | 사용자가 `AGENTS.md` + 필요한 docs를 첨부 |

- 실제 쓰는 도구의 포인터 파일만 만든다 (사용 도구는 `rules/01`).
- 포인터 파일에 규칙을 복사하지 않는다. 규칙이 여러 곳에 있으면 서로 어긋난다.

## 2. 항목 출처 태그와 상태 표기

### 출처 태그 — 각 결정 항목 제목 옆에 붙는다

| 태그 | 의미 | 처리 |
|---|---|---|
| 🧩 메타 | 모든 프로젝트 공통 기본값 (사용자의 상시 작업 방식) | 이미 기본값이 들어 있다. 업무정의서·사용자 지시가 다르면 덮어쓰고 99에 기록 |
| 📋 업무정의서 | 프로젝트마다 달라지는 값 | 업무정의서에서 찾아 채운다. 없으면 💬 인터뷰로 넘어간다 |
| 💬 인터뷰 | 업무정의서로 정할 수 없어 사용자 확인이 필요한 값 | 선택지 + 추천안과 함께 질문 |

### 상태

| 표기 | 의미 |
|---|---|
| ❓ 미결정 | 아직 정해지지 않음. **하나라도 남아 있으면 개발 금지** |
| 🧩 기본값 | 메타 기본값이 적용된 상태. 개발 가능. 덮어쓰면 ✅로 바꾼다 |
| 🔸 추정 | 업무정의서에서 추론했지만 명시되지 않은 값. 인터뷰에서 한꺼번에 확인받아 ✅로 바꾼다 |
| ✅ 결정 | 업무정의서에 명시됐거나 사용자가 확인함 |
| ➖ 해당없음 | 이 프로젝트에 필요 없음 (사용자 확인 후) |

문서 상단 `문서 상태`는 모든 항목이 ✅·🧩·➖가 되면 `✅ 완료 (YYYY-MM-DD)`로 바꾼다.

## 3. 초기 구성 절차 (Phase 0 → 4)

### Phase 0. 입력 확인
- 업무정의서 경로, 참조 자료(DB 접속 정보·외부 API 키 위치·포트 등)를 확인한다.
- 업무정의서가 없으면 **00_PROJECT부터 인터뷰 모드**로 진행한다 (3장 인터뷰 규칙).
- 대화에서 사용자가 이미 밝힌 정보는 질문하지 말고 먼저 기록한다.

### Phase 1. 업무정의서 흡수
1. 업무정의서 전체를 읽고 `rules/00`~`09`의 📋 항목을 채운다. 명시된 값은 ✅, 추론한 값은 🔸.
2. 업무정의서의 **업무 용어**(엔티티·상태·역할·행위)를 뽑아 `rules/09` 4장 업무 용어 사전에 등록한다. 이후 모든 코드·DB·API·UI 태그 이름은 이 사전에서 가져온다.
3. 업무정의서에 기능·화면·API·배치·데이터가 나오면 `specs/`의 **목록 표**에 📝 설계 상태로 등록한다. (상세 명세는 구현 직전에 작성)
4. 업무정의서가 🧩 기본값과 충돌하면 업무정의서를 따르고 `99_DECISIONS.md`에 "메타 기본값 → 업무정의서 값"으로 기록한다.
5. 해당 없는 문서(예: AI 미사용 → 05·14·16)는 ➖ 후보로 표시한다.

### Phase 2. 갭 인터뷰
1. 남은 ❓·🔸를 모아 **한 번에 한 주제** 단위로 묻는다. 밀접한 항목은 2~3개까지 묶는다. 🔸는 목록으로 보여주고 일괄 확인받는다.
2. 질문에는 반드시 **선택지 + 추천안 + 이유**를 함께 제시한다. 추천 기준은 `rules/00`의 프로젝트 성격이다.
3. "알아서 해줘"·"권장으로 진행"이면 추천값을 기록하되 **어떤 값을 골랐는지 요약해 보고**한다.
4. 순서는 파일 번호 순(00 → 09). 프로젝트 성격이 먼저 정해져야 뒤 추천이 정확해진다.

### Phase 3. 하네스 파일 생성
rules 문서가 확정되면 리포 루트에 아래를 만든다. **내용의 원본은 언제나 `docs/agent/`이고, 하네스 파일은 그 요약·포인터다.** (중복 서술 금지 — 규칙을 바꿀 때는 docs/agent만 고친다)

| 파일 | 용도 |
|---|---|
| `AGENTS.md` | 표준 진입점 본문 (`ENTRY_TEMPLATE.md` 1장) |
| 도구별 포인터 파일 | 사용하는 도구만 — `CLAUDE.md`, `GEMINI.md`, `.agents/rules/` 등 (0-3, `ENTRY_TEMPLATE.md` 2장) |
| 도구별 설정 (선택) | 해당 도구를 쓸 때만 — 권한 허용 목록(예: `.claude/settings.json`), MCP 설정(도구 규약 위치 한 곳). 없어도 동작해야 한다 |
| `.env.example` | 모든 환경변수 키 목록 (값은 비우거나 예시) — `.env`는 커밋 금지 |
| `restart_server.sh` / `stop_server.sh` | 서버 재시작·중지 표준 스크립트 (06 참조) |
| `.vscode/launch.json` | 서버 디버그 실행 구성 (포트는 06) |
| `playwright.config.*` + `tests/e2e/` | headless 검증 기본 구성 (07 참조) |
| `.gitignore` | `.env`, 빌드 산출물, 테스트 리포트, 로컬 데이터 |

- 사용자의 **글로벌 프롬프트**(홈 디렉터리의 도구별 전역 설정)는 수정하지 않는다.
- L1·L2 수준이면 위 파일들의 경로와 전체 내용을 출력하고, 사용자가 만든 뒤 알려주면 다음으로 넘어간다.
- 기존 하네스 파일이 있으면 읽고 병합한다. 중복 파일은 하나로 합치고 불필요한 파일은 사용자 확인 후 삭제한다.
- `docs/` 루트는 사용자 지침서·업무정의서 폴더다. 에이전트 문서는 `docs/agent/`에만 둔다.

### Phase 4. 개발 시작 확인
아래를 **모두** 만족하기 전에는 프로젝트 코드를 작성하지 않는다.

- [ ] `rules/` 전체에 ❓·🔸가 없음 (✅·🧩·➖만 존재)
- [ ] 하네스 파일 생성 완료, `restart_server.sh`로 빈 서버가 뜨고 Playwright 스모크 1건 통과 (L1·L2는 사용자가 실행한 결과로 확인)
- [ ] 하네스 구성 자체를 첫 커밋으로 남김 (`chore: 하네스 초기 구성`)
- [ ] 사용자에게 "모든 결정이 완료되었습니다. 적용된 메타 기본값: …. 개발을 시작할까요?"라고 확인받음

`specs/`는 개발 전에 다 채우지 않아도 된다. 단,
- **개별 기능 구현 전에** 그 기능의 API·화면·배치 명세를 먼저 작성한다.
- **실사용(배포·실데이터·실발송·실결제) 전에** `specs/13_OPERATIONS.md`를 작성한다.

## 4. 바이브 코딩 운영 루프 (개발 중 상시 규칙)

> 이 장이 하네스의 핵심이다. 사용자는 짧게 지시하고("마무리까지 진행", "검증과 이슈 해결", "부족한 부분은 판단해 진행"), AI는 아래 루프로 완결한다.

1. **계획**: 파일 3개 이상 또는 스키마·API 변경이 있는 작업은 먼저 짧은 계획(변경 파일·검증 방법)을 제시한다. 사용자가 "진행"이라 하면 끝까지 수행한다.
2. **명세 우선**: 새 API·화면·배치·컬렉션은 specs/rules에 먼저 기록 → 구현.
3. **구현**: 기존 코드 관례를 따른다. 이름은 `rules/09` 업무 용어 사전에서 가져오고, 사전에 없는 업무 용어가 필요하면 사전에 먼저 등록한다. 환경값은 루트 `.env` 한 곳에서만 읽는다.
4. **자가 검증**: `restart_server.sh` → Playwright headless로 실제 사용자 흐름 검증 → 빌드·린트 확인. 실패하면 원인 수정 후 재검증, **최대 5회 반복**. 5회 안에 못 끝내면 멈추고 원인·시도·남은 이슈를 보고한다.
5. **커밋 (생략 금지)**: 검증을 통과한 **업무 묶음이 끝날 때마다 즉시 커밋**한다. 무엇이 업무 묶음인지, 메시지 형식은 `rules/08` "커밋 시점"을 따른다. 여러 묶음을 한 커밋에 섞지 않고, 사용자가 "커밋하지 마"라고 하지 않는 한 묶음을 끝내고 커밋 없이 다음 묶음으로 넘어가지 않는다. (L1·L2는 커밋 명령을 출력)
6. **동기화**: 코드 변경으로 바뀐 API·화면·배치·스키마를 같은 커밋 안에서 specs에 반영한다. 이슈 대응이면 `changelog.md`에 기록.
7. **보고**: 무엇을 했는지, 검증 결과(통과/실패 그대로), **만든 커밋 목록(해시·메시지)**, 판단해서 정한 것, 남은 일을 짧게 보고한다.

### 판단 위임 규칙
- "부족한 부분은 판단해 진행" 지시가 있으면 업무정의서 의도에 맞게 빈틈을 채우되, 판단한 내용은 보고에 명시한다.
- 단, 아래는 위임받았어도 **반드시 먼저 확인**한다: 데이터 삭제·DB 초기화, 실발송(문자·메일·알림), 실결제, `main` 브랜치 직접 반영·force push, 외부 서비스에 데이터 공개, 이미 ✅된 결정 변경.

## 5. 문서 유지 규칙 (문서 우선 원칙)

1. **문서 → 코드 순서**: 설계 변경은 문서를 먼저 고치고 코드를 맞춘다.
2. **결정 변경 이력**: ✅·🧩 결정을 바꾸면 `99_DECISIONS.md`에 (날짜, 문서, 항목, 이전 → 새, 이유)를 남긴다. 폐기된 방안은 다시 제안하지 않는다.
3. **산출물 동기화**: 코드와 문서가 다르면 문서가 틀린 것이므로 즉시 고친다.
   - 예외(원본 전환): 자동 생성 API 문서(Swagger 등) 도입 후에는 코드가 원본(`specs/10` 0장), 마이그레이션 도구 도입 후에는 마이그레이션 파일이 원본(`rules/04`). 문서에는 목록·설계 의도만 유지한다.
4. **충돌 요청 처리**: 사용자 요청이 기존 결정과 충돌하면 조용히 따르지 말고 충돌 사실을 알리고 결정 갱신 여부를 확인한다.
5. **시크릿 금지**: 문서·커밋·로그·프롬프트 히스토리에 실제 키·토큰·비밀번호·개인 연락처를 적지 않는다. 키 이름만 `.env.example`에 둔다.
