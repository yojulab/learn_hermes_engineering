# AGENT_GUIDE — AI 에이전트 작업 지침서

> **이 문서는 사람이 아니라 AI 에이전트가 읽는 문서입니다.**
> 이 폴더의 문서 세트를 발견한 AI는 코드를 작성하기 전에 반드시 이 지침을 따라야 합니다.

## 사용 방법 (사람용 안내)

1. 새 프로젝트를 시작할 때 이 템플릿 폴더 전체를 복사하여 프로젝트의 `docs/` 폴더로 넣는다.
2. AI에게 "docs/AGENT_GUIDE.md를 읽고 인터뷰를 시작해줘"라고 요청한다.
3. AI의 질문에 답하면 문서가 채워지고, 모두 채워지면 개발이 시작된다.

## 1. 문서 세트 구성

폴더 구조가 곧 문서의 성격이다. (아래 경로는 모두 문서 세트 루트 기준)

```
docs/
├── AGENT_GUIDE.md      ← 이 문서 (진입점)
├── 99_DECISIONS.md     ← 결정 변경 이력
├── rules/              ← 규칙 문서: 개발 시작 전에 모든 필수 항목이 결정되어야 함
└── specs/              ← 산출물 문서: 개발이 진행되면서 계속 추가·갱신됨
```

## 2. 상태 표기 규칙

모든 결정 항목은 아래 상태 중 하나를 가진다.

| 표기 | 의미 |
|---|---|
| ❓ 미결정 | 아직 사용자에게 확인받지 않음. **이 상태가 남아 있으면 개발 금지** |
| ✅ 결정 | 사용자 확인 완료 |
| ➖ 해당없음 | 이 프로젝트에서는 필요 없음 (사용자 확인 후 표기) |

문서 상단의 `문서 상태`는 문서 내 모든 필수 항목이 ✅ 또는 ➖가 되었을 때 `✅ 완료`로 변경한다.

## 3. 인터뷰 진행 규칙

1. **사전 제공 정보 먼저 반영**: 사용자가 대화에서 이미 밝힌 정보(예: "이번엔 협업이니까 헥사고날로 하자", "DB는 PostgreSQL 쓸 거야")가 있으면, 질문하지 말고 먼저 해당 문서에 기록하고 ✅ 처리한다. 그 후 남은 ❓ 항목만 질문한다.
2. **질문 순서**: `rules/00_PROJECT.md`부터 파일 번호 순서대로 진행한다. 프로젝트 성격이 먼저 정해져야 뒤 문서의 추천이 정확해진다.
3. **한 번에 한 주제**: 질문은 한 번에 하나의 주제만 한다. 밀접하게 연관된 항목(예: DB 종류 + 버전)은 2~3개까지 묶어서 물어볼 수 있다.
4. **선택지와 추천 제시**: 질문할 때는 반드시 선택지를 함께 제시하고, 프로젝트 성격(`rules/00_PROJECT.md` 기준)에 맞는 추천안과 그 이유를 말한다.
5. **"알아서 해줘" 처리**: 사용자가 추천을 요청하거나 위임하면, 추천값과 이유를 제시하고 **확인을 받은 후** 기록한다. 확인 없이 임의로 ✅ 처리하지 않는다.
6. **기록 형식**: 결정이 나면 즉시 해당 문서의 `결정`, `이유`, `결정일`(YYYY-MM-DD)을 채우고 상태를 ✅로 바꾼다.
7. **해당 없는 문서 건너뛰기**: 프로젝트에 프론트엔드가 없거나 AI를 쓰지 않는 등 문서 전체가 불필요하면, 사용자에게 확인 후 문서 상단 상태를 `➖ 해당없음`으로 표기하고 건너뛴다.

## 4. 개발 시작 조건

아래 조건을 **모두** 만족하기 전에는 프로젝트 코드를 작성하지 않는다.

- [ ] 규칙 문서(`rules/` 전체)의 모든 필수 항목이 ✅ 또는 ➖ 상태
- [ ] 사용자에게 "모든 결정이 완료되었습니다. 개발을 시작할까요?"라고 최종 확인을 받음

산출물 문서(`specs/` 전체)는 예외: 개발 시작 전에 다 채우지 않아도 된다. 단,
- **개별 기능을 구현하기 전에** 그 기능의 API 명세·화면 설계·배치 명세를 먼저 작성하고 구현한다.
- **실사용(배포 또는 실데이터·실계좌 연동)을 시작하기 전에** `specs/13_OPERATIONS.md`(런북)를 작성한다.

## 5. 개발 중 문서 유지 규칙 (문서 우선 원칙)

1. **문서 → 코드 순서**: 설계 변경이 필요하면 문서를 먼저 수정하고, 코드를 문서에 맞춘다. 반대 방향 금지.
2. **결정 변경 이력**: 이미 ✅된 결정을 바꿀 때는 반드시 `99_DECISIONS.md`에 변경 이력(날짜, 항목, 이전 값 → 새 값, 이유)을 남긴다.
3. **산출물 문서 동기화**: API·화면·배치·테이블을 추가/변경/삭제하면 같은 작업 안에서 해당 산출물 문서도 갱신한다. 코드와 문서가 다르면 문서가 틀린 것이므로 즉시 고친다.
   - 단, **원본 전환 규칙**이 적용된 영역은 예외: API 상세는 자동 생성 문서(Swagger 등) 도입 후 코드가 원본(`specs/10_API_SPEC.md` 0장), DB 스키마는 마이그레이션 도구 도입 후 마이그레이션 파일이 원본(`rules/04_DATABASE.md` 4장). 이 경우 문서에는 목록·설계 의도만 유지한다.
4. **문서와 충돌하는 요청 처리**: 사용자의 요청이 기존 결정과 충돌하면, 조용히 따르지 말고 충돌 사실을 알리고 결정을 갱신할지 확인한다.
