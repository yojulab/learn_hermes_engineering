# 16. AI 모델 고도화 A/B/C 비교 프로토콜

> 문서 상태: ✅ 실측·채택 완료 (2026-08-19) — §5 비교표·판정 확정, **C-1 공격안(th 0.35 + k 5 + margin 0) 운영 기본값 전환·baseline 이관까지 반영** (99_DECISIONS 참조).
> 목적: 이번 주 **미식별(open-set) 트랙**의 세 접근 A·B·C를 **같은 데이터·같은 조건·같은 지표**로 재서 공정하게 비교한다. 감이 아니라 회귀 게이트 실측으로 고르는 것이 이 프로젝트의 방식이다 (rules/05).

## 1. 이번 주 고도화 라인업

| 고도화 | 요일 | 방향 제시 | 접근 | 상태 |
|---|---|---|---|---|
| **A** | 화 | 황서범 | 비율 검사 (open-set margin) — 1등 절대값 + 1등−2등 격차 | ✅ 완료 (PR #165) |
| **B** | 수 | 민선아 | 블러–인식 오류 감사 (`tools/blur_error_audit.py`, `feat/SA-blur-error-audit`) — Restormer(디블러링) 채택의 사전 검증. **분석 트랙이라 4지표 운영점 없음** | ✅ 감사 완료 (2026-08-19) — 결론: 현 표본에서 채택 근거 불성립 (§5-B) |
| **C** | 목 | 진영 | **C-1** 갤러리 집계 top-k 평균 (`feat/openset-topk-aggregation`) · C-2 ROI (관측 선택 — 4지표 대상 아님) | ✅ C-1 실측 완료 (2026-08-19) — **§6 판정 승자** / C-2 📝 설계 |
| (별도 트랙) | 금 | 황서범 | 가림(occlusion) 합성 — 공개 **액세서리 에셋**을 등록 얼굴에 씌워 파인튜닝 열화 짝에 추가 | Phase 0 실측(가림 확인) → 파인튜닝 ❌ 채택 불가(오통과 붕괴 0.7→18.5%) → **재설계 채택 ②: 탐지 단계 발행 품질 게이트**(비파인튜닝, 기본 off — 2026-08-20). 근본 해결(negative 파인튜닝 ①)은 보류(#135). 상세 §Phase 1 |

A·B·C는 **미식별 트랙 안의 세 접근**이고, 금요일은 두 번째 트랙(합성)이다.

> ⚠️ **정정 (Phase 1 실측 2026-08-20, 아래 §Phase 1)**: "공개 *얼굴* 데이터셋 불필요"는
> **틀렸다.** R100 해상도 파인튜닝을 우리 11명만으로 돌렸더니 개방집합 오통과가 0.7 → 18.5%로
> **붕괴**했다(변별력 상실). InfoNCE negative가 11명뿐이라 "남과 구별" 신호가 모자란 게 원인 —
> **negative 다양성(=공개 얼굴 데이터셋)이 오히려 필요**하다. 아래 원문은 착수 시점 가설로 남겨 둔다.
>
> **합성(가림) 트랙 설계 (2026-08-20, ⚠ 위 정정 참조)**: ~~공개 *얼굴* 데이터셋은 **불필요**~~ — 파인튜닝
> 손실이 "같은 사람의 가림 전/후 임베딩 일치"(cross-resolution InfoNCE, `finetune/losses.py`)라,
> 우리 등록자 얼굴 + 공개 *액세서리* 에셋(마스크·선글라스·안경 RGBA PNG)이면 짝이 완성된다.
> 가림은 "또 다른 열화"라 `train.py`·`losses.py`를 손대지 않고 `augment_lowres`(해상도) 옆에
> **`augment_occlusion`(가림)** 을 두어 같은 열화 셋에 append한다. 파이프라인:
> **Phase 0** `tools/occlude_probe.py`로 가림 민감도 **측정**(만들 가치 판정) → **Phase 1**
> `tools/augment_occlusion.py`로 학습셋 합성 → `finetune/train.py` → **`regression_gate`
> 개방집합 before/after 게이트**(오통과 오르면 롤백, #135) → 갤러리 재생성(#114·#118).
> ⚠ InfoNCE negative가 우리 로스터(~11명)로 한정돼 "남과 구별" 다양성이 약함 — 게이트 필수.
> ⛔ 합성 파생본은 **학습셋 전용**, 등록 갤러리엔 절대 넣지 않는다(회전 증강 갤러리 사고와 동일).

### Phase 0 실측 — 가림 민감도 (2026-08-20, CTO 맥 중앙 실행)

`occlude_probe.py`로 §4 평가셋(선분류_0807, 2,857장)에 가림을 씌워 현행 **C-1(th 0.35+k5+m0)**
기준선(깨끗한 원본: 통과 80.8 / 오식별 1.2 / 오통과 0.7)과 대조했다. **그린 가림(alpha=1,
순수 차폐)** 이라 실물보다 보수적(worst-case)이다.

| 가림 | 탐지 유지율 | 등록자 통과 | **낙폭** | 오식별 | 오통과 |
|---|---|---|---|---|---|
| 마스크 | 75.8% | 69.0 | **−11.8%p** | 0.1 | 2.4 |
| 선글라스 | 81.5% | 66.8 | **−14.0%p** | 0.6 | 0.8 |
| 안경(테) | 80.7% | 62.5 | **−18.3%p** | 0.6 | 0.8 |

**판정: Phase 1 GO — 가림은 실제 실패 원인이다.** 세 가림 모두 통과율이 허용(−3%p)을
크게 넘겨 회귀(−11.8~−18.3%p). 읽을 점:

1. **눈 영역(안경·선글라스)이 입 영역(마스크)보다 인식에 더 치명적** — periocular이 임베딩의
   핵심이라 예상과 일치. (단 "안경"은 그린 테가 불투명이라 실물 투명 렌즈보다 **과대추정**.
   실측 순위의 절대값은 실물 PNG로 재보정 필요 — Phase 1 준비 시 `--assets`.)
2. **탐지 손실 18~24%는 인식이 아니라 YuNet 문제** — 인코더 파인튜닝으로 **못 고친다**
   (표본이 897→775~787로 줄어든 원인). 파인튜닝은 "탐지된 얼굴의 인식 하락"만 겨냥한다.
3. **오통과는 거의 안 움직임(≤2.4%)** — 가림은 오통과가 아니라 **놓침(miss)**을 만든다.
   출결 "잔존 증거" 맥락에선 가려진 학생 = 알림 누락이지, 낯선 사람 오발송은 아니다.

⚠ 이 실측은 그린 가림 기준의 **하한 신호**다 — 실물 에셋으로 Phase 1 학습 후 개방집합
before/after 게이트를 다시 통과해야 채택이다(오통과 악화 시 롤백, #135).

### Phase 1 실측 — R100 파인튜닝 시도 (2026-08-20, GPU 서버) → ❌ 채택 불가 (#135의 답)

가림 학습 전에 **해상도 열화 파인튜닝**으로 GPU 파이프라인을 먼저 관통시켰다(learnpipe 검증 +
1·2차 "판정 불가"를 게이트로 결판). 등록 HR 660장 + `augment_lowres` 3,300장으로 **R100 헤드만**
cross-resolution 파인튜닝(5 epoch, GPU 3번, InfoNCE 분리도 +0.56→+0.74) → merge → onnx →
실 probe(선분류_0807)로 게이트.

**게이트 (th 0.35 · m0 · k5) — 파인튜닝 R100 + 원본 AdaFace:**

| 지표 | 원본 | 파인튜닝 | |
|---|---|---|---|
| 등록자 통과 | 80.8 | 86.5 | +5.7%p |
| 등록자 오식별 | 1.2 | 2.0 | +0.8 |
| **미등록 오통과** | **0.7** | **18.5** | **+17.8%p 💥 회귀** |

**임계값 스윕 — 파인튜닝 모델은 모든 지점에서 원본에 짐(dominated):**

| 맞추는 기준 | 원본 | 파인튜닝 |
|---|---|---|
| 오통과 0.7%로 고정 | th0.35 → 통과 **80.8** | th0.45 → 통과 **77.8** (−3.0%p) |
| 통과 80.8%로 고정 | th0.35 → 오통과 **0.7** | th0.42 → 오통과 **1.5** (2배) |

- 미등록 최고 유사도 **0.589 → 0.662**, 상위 1% **0.349 → 0.429** — 낯선 사람이 등록자에 **더 닮게**
  이동(분포 자체가 올라가 어떤 임계값도 원본 분리를 못 회복). 스윕 중 `NaN/overflow in matmul`
  경고까지(일부 퇴화 임베딩) — 모델 불안정.
- **판정: ❌ 채택 불가·롤백.** 서빙은 원래 안 바뀜(파인튜닝 onnx 미배포). C-1 운영점 유지.
- **원인 = 변별 신호 부족.** 11명·해상도만으로 InfoNCE를 돌리면 공간이 불변성 쪽으로 붕괴해
  낯선 사람까지 당겨온다 — **회전 증강 갤러리 사고(오통과 18.5%)와 같은 병**(rules/05 line 249).
- **가림(Phase 1 본편)에의 함의**: 가림은 불변성을 더 밀어붙이므로 같은 설계면 **더 나빠질 위험**.
  재설계 3안: ① negative 다양성(공개 얼굴 데이터셋) 투입 ② 비파인튜닝 완화(가림 심하면 **탐지
  단계 발행 억제** — 오통과 대신 놓침 선택, 출결 맥락에 더 안전) ③ 트랙 보류(C-1 유지, 발표
  근거는 "게이트가 붕괴를 잡아냄").

### Phase 1 재설계 — 채택 ②: 탐지 단계 발행 품질 게이트 (2026-08-20)

파인튜닝(①)은 데이터 수급+GPU가 커 보류하고, **비파인튜닝 위생 게이트(②)**를 채택했다.
착수 전 "det_score가 가림 신호로 쓸 만한가"를 측정(250장, clean vs 그린 가림):

| | clean | mask | sunglasses | glasses |
|---|---|---|---|---|
| det_score 중앙 | 0.919 | 0.892 | 0.889 | 0.882 |

- **가림이 det_score를 거의 안 낮춘다(0.92→0.88).** YuNet은 가려도 얼굴을 자신 있게 찾는다 —
  즉 **det_score는 약한 가림 필터**다. floor 0.85면 clean 1% 손실에 가림 ~15%만 트림(0.90은
  clean 17%까지 잘라 못 씀). 나머지 85% 가림은 det_score가 높아 통과한다.
- **결론**: 탐지 단계 억제는 "가림 해결"이 아니라 **"불확실한 최악 품질 인식을 안 믿는 위생 노브"**다.
  Phase 0가 보인 대로 가림의 해악은 **놓침**이지 오통과가 아니라, 억제는 놓침만 늘린다(출결은
  반복 통과로 만회). 그래서 **기본 off의 config 노브**로만 남긴다:
  - `DETECTION_EMIT_MIN_DET_SCORE`(기본 0=off) — det_score 미달이면 발행 억제, `lowq_suppressed_total` 관측.
  - 코드: `EventEmitter.emit` 최상단 게이트(인라인·2단계 공통), `test_emit_quality_gate`.
- **진짜 가림 해결은 여전히 ①(negative 다양성 파인튜닝)** — 등록 인원이 늘거나 공개 얼굴셋을
  확보하면 그때 재개한다(#135). 그 전까지 가림은 **문서화된 한계**(놓침, 반복 통과로 완화)다.

## 2. 대전제 — 평가 데이터 위치와 공정성

비교가 성립하려면 세 접근을 **동일 데이터·동일 머신·동일 조건**에서 재야 한다. 그런데 기준 평가셋(등록 897 + 미등록 135장 CCTV 크롭)은 **CTO 맥 로컬의 개인정보**다(`~/Desktop/영상 추출/선분류_0807`). 팀 규칙상 **재공유·커밋·공용 GPU 서버 적재 금지**(rules/02·04, 개인정보 보존기간 = LMS period).

그래서 워크플로를 이렇게 잡는다:

- **B·C 담당자는 "산출물"을 만들어 전달한다** — 알고리즘 변경이면 브랜치(코드), 모델 변경이면 `.onnx` 파일.
- **평가는 데이터가 있는 한 곳(CTO 맥)에서 중앙 실행한다** — 그래야 A·B·C가 같은 데이터·머신에서 재져 비교가 성립하고, 개인정보도 흩어지지 않는다.
- **개발 중 자가 점검**이 필요하면 CTO와 한 번씩 맞춰 돌린다. 평가셋이 CTO 맥에만 있으므로 담당자 혼자서는 실측이 안 된다 — 이 점만 미리 합의해 둘 것.

## 3. 담당자 산출물 — 두 가지 케이스

### 케이스 1 — 알고리즘 변경 (A처럼 매칭·거절 방식을 바꾸는 경우)
- 브랜치에 **코드만** 커밋한다.
- ⚠ **얼굴 데이터·모델(`.onnx`)·`registry.json`은 커밋 금지** (rules/02·04).
- 평가는 그 브랜치를 체크아웃해 표준 커맨드를 그대로 돌린다.

### 케이스 2 — 모델 변경 (파인튜닝 등 가중치를 바꾸는 경우)
- 산출물 `.onnx` 파일을 CTO에게 **별도 전달**한다 (커밋 금지 — 대용량·비공개).
- 파일명을 알려주면 평가 시 `--arcface`/`--adaface`로 지정한다.
- ⚠ 모델을 바꿨으면 `webapp/models/CHECKSUMS.txt` 지문 갱신도 함께 (rules/05, 이슈 #114) — 단 이건 **채택이 확정된 뒤** 서빙 반영 단계에서 한다. 비교 단계에서는 파일만 있으면 된다.

## 4. 표준 실행 커맨드 (CTO 맥, 각 고도화마다)

### 고정 조건 — 절대 바꾸지 말 것
이 6개가 하나라도 달라지면 A·B·C 비교는 무효다.

```bash
cd ~/Desktop/AutoGT/webapp
.venv/bin/python tools/eval_openset.py \
  --gallery data/enroll \
  --gallery-session 20260813 \
  --max-gallery 30 \
  --limit-per-person 120 \
  --probe "$HOME/Desktop/영상 추출/선분류_0807" \
  --threshold <운영점> --margin <운영점>
```

| 고정 인자 | 값 | 이유 |
|---|---|---|
| `--gallery` | `data/enroll` | 등록 사진 루트 |
| `--gallery-session` | `20260813` | 갤러리 촬영일 고정 (조회와 다른 날 — 세션분리) |
| `--max-gallery` | `30` | 인당 갤러리 장수 |
| `--limit-per-person` | `120` | 조회 장수 상한 (한 사람이 표본 지배 방지) |
| `--probe` | CTO 맥 CCTV 크롭 루트 | 개인정보 — 이 머신에서만 |
| 모델 | 서빙 기본 (`glintr100`+`adaface_ir101`) | 모델 변경 접근만 아래로 교체 |

### 케이스별 추가

- **알고리즘 변경**: B/C 브랜치 체크아웃 후 위 커맨드 그대로.
- **모델 변경**: `--arcface <새모델>.onnx --adaface <새모델>.onnx` 추가.
- **C-1 (갤러리 집계)**: `--topk <k>` 추가. **k를 바꿀 때마다 재실행**해야 한다 — margin은 top-1·top-2만 보므로 `--sweep`이 훑을 수 있지만, topk는 점수 자체를 바꿔 `rank`를 다시 태운다(임베딩이 다시 돈다). 후보 구간 **k=3~5**, `--topk 1`은 종전 max와 비트 단위로 같다

  §6 판정이 깔끔하려면 **세 줄**이 필요하다 — 직교성 확인이 이 고도화의 쟁점이기 때문이다:

  | 줄 | 커맨드 | 목적 |
  |---|---|---|
  | C 단독 | `--margin 0 --topk <k>` | A와 독립적인 순수 효과 |
  | A 단독 | `--margin 0.10 --topk 1` | 이미 있음 — 76.6 / 2.3 / 21.1 / 3.7 |
  | A + C | `--margin 0.10 --topk <k>` | 겹치면 합쳐도 안 오른다 |

- **C-2 (ROI)**: ⚠ **§5 비교표에 올리지 않는다.** 두 기전(큐 우선순위·발행 보류) 모두 **판정 기준을 바꾸지 않고 어느 관측을 쓸지만 정하므로** 4지표가 움직이지 않는다 — 평가 도구에는 큐도 시간축도 없다. 선행으로 `tools/recover_probe_bbox.py`가 조회 크롭의 프레임 좌표를 복원해야 하고(지금 평가셋은 얼굴 크롭 파일 모음이라 **좌표도 시간축도 없다**), 산출물은 **통과율·안밖 성공률 격차·전이 시간 분포**다 (rules/05 참조)

### 운영점 찾기
각 접근의 최적 운영점은 `--sweep`으로 훑는다 (margin 고정, 임계값을 훑어 표로 출력):

```bash
.venv/bin/python tools/eval_openset.py [...고정조건...] --margin 0.10 --sweep
```

각 접근은 **자기 최적 운영점**을 골라 그 지표를 보고한다 (운영점 값도 함께 — 투명성).

## 5. 출력 → 비교표

`eval_openset.py`는 4지표를 낸다:

```
 임계값   등록자 통과   오식별   놓침   미등록 오통과
  0.38       76.6%     2.3%   21.1%      3.7%  ←
```

각 담당자는 **자기 운영점의 한 줄**을 보고하고, 목요일 저녁에 아래 표로 합친다.

| 고도화 | 접근 | 운영점 | 등록자 통과 | 오식별 | 놓침 | **미등록 오통과** |
|---|---|---|---|---|---|---|
| (기준) | 6차 임계값만 | th 0.40 | 78.1 | 3.9 | 17.9 | 11.9 |
| **A** | 비율 검사 | th 0.38 + m 0.10 | 76.6 | 2.3 | 21.1 | 3.7 |
| **B** | 블러–오류 감사 | *(분석 트랙 — §5-B)* | — | — | — | — |
| **C** | 갤러리 top-k 평균 | **th 0.35 + k 5** (m 0) | **80.8** | 1.2 | **17.9** | **0.7** |
| A+C | margin + top-k | th 0.35 + m 0.10 + k 5 | 77.8 | **0.6** | 21.6 | 0.7 |

*표본: 등록자 조회 897장 / 미등록 조회 135장. 기준·A는 2026-08-18, B·C·A+C는 2026-08-19 측정 — 전부 §4 고정 조건(같은 데이터·같은 맥·같은 갤러리 세션) 그대로.*

### §5-C 실측 상세 — C-1 (2026-08-19, CTO 맥 중앙 실행)

C 담당자가 §4에 적어 둔 세 줄 프로토콜대로 k=3·4·5 각각 C 단독(margin 0)과 A+C(margin 0.10)를 쟀다 (`feat/openset-topk-aggregation` 체크아웃, 표준 커맨드 + `--topk`).

**C 단독 (margin 0) — 오통과 0.7% 달성 운영점들만 발췌:**

| k | 임계값 | 통과 | 오식별 | 놓침 | 오통과 |
|---|---|---|---|---|---|
| **5** | **0.35** | **80.8** | 1.2 | 17.9 | **0.7** |
| 3 | 0.38 | 78.7 | 1.4 | 19.8 | 0.7 |
| 4 | 0.38 | 78.5 | 0.9 | 20.6 | 0.7 |
| 5 | 0.38 | 77.8 | 0.6 | 21.6 | 0.7 |

**A+C 결합 — 직교 가설은 기각, 겹치는 관계다:**

- k=5 + m 0.10 @0.35: 77.8 / 0.6 / 21.6 / 0.7 — margin을 얹어도 **오통과는 0.7%에서 더 내려가지 않고** 통과만 −3.0%p 깎인다 (80.8 → 77.8).
- 해석: top-k 평균이 "낯선 사람이 우연히 한 장과 맞는" 극단값 추첨을 점수 단계에서 이미 희석하므로, 같은 현상을 격차로 걸러내던 margin의 몫이 사라진다. margin의 잔여 효과는 오식별 소폭 개선뿐(1.2% → 0.6%, 897장 중 ~11장 → ~5장).
- 미등록 점수 분포도 같은 방향: 미등록 최고 유사도가 max 집계 대비 내려가고(k=5에서 0.589), 상위 1%는 0.349.

**주의 (판정에 달아 두는 각주):**

- 오통과 0.7% = **135장 중 1장**이다. 0.7 vs 1.5의 차이가 크롭 한 장이라, A margin 때와 같은 소표본 경고가 그대로 적용된다 — 미등록 표본 보강 후 held-out 재확인 필요.
- 승자 운영점의 임계값 0.35는 미등록 상위 1% 유사도(0.349)와 **간발의 차**다. 등록 인원이 늘면 이 여유부터 무너진다(05_AI 경고 그대로). 보수 대안은 **k=5 + th 0.38**(77.8/0.6/21.6/0.7 — 오통과 동일, 여유 ↑, 통과 −3.0%p) 또는 **k=3 + th 0.38**(78.7/1.4/19.8/0.7). 채택 단계에서 공격/보수를 고른다.

### §5-B 실측 상세 — B (블러–오류 감사, 2026-08-19)

서빙 변경 없는 **분석 트랙** — "흐릴수록 인식 오류가 늘어나는가"를 재서 Restormer(디블러링) 채택의 근거를 만들려는 사전 검증이다. A 운영점(0.38+0.10) 위에서 §4 고정 조건 그대로 1,050장을 감사했다.

- 원시 상관 r = **+0.159** (선명할수록 오류?) — 교란이다: 크롭 면적과 Laplacian 선명도가 강하게 얽혀 있다(log-log r = −0.74).
- 면적·인물·세션 통제 후 부분상관 r = **−0.146** — "흐릴수록 오류" 방향의 **약한** 연관만 남는다.
- 사분위 오류율은 단조가 아니다(15.2 → 12.6 → 19.8 → **39.5%** — 가장 "선명한" 사분위가 최악).
- **결론(도구 자체 판정 그대로): 현재 수치만으로 디블러링 채택을 결정하지 않는다.** 기존 크롭 파이프라인의 blur≥50 필터 때문에 강한 블러 표본 자체가 평가셋에 없다 — 후속 조건은 무필터 크롭 재수집(`tools/suggest_lowblur_labels.py`) 후 재감사.

### §6 적용 결과 (2026-08-19 판정)

1. **미등록 오통과 최저**: C 단독·A+C 모두 0.7%로 동률 (A 3.7%, 기준 11.9% 탈락).
2. **등록자 통과 최고**: C 단독 k=5 @0.35 = **80.8%** (A+C 최고는 77.8%).
3. → **승자: C-1 갤러리 top-k 평균, 운영점 th 0.35 + k 5 (margin 0)** — 기준선과 A를 **모든 지표에서** 이기는 명확한 승. A는 §6 규칙대로 교체 후보 자리를 내준다.

⚠ 이 판정은 **비교표의 결론**이고 채택은 별도 단계다: C 브랜치(PR) 머지 → `.env`/config 운영점 변경(MATCH_THRESHOLD·MATCH_MARGIN·MATCH_TOPK) → `baseline.json` 갱신(회귀 게이트 조건 이관) → 상단 각주의 공격(0.35)/보수(0.38) 선택. margin 코드는 **제거하지 않는다** — 등록 인원이 늘어 재측정할 때 다시 유효해질 수 있는 독립 손잡이다.

## 6. 비교 판정 규칙 (미리 고정 — 목요일에 안 헷갈리게)

우선순위 순으로:

1. **미등록 오통과** (낮을수록 좋음) — 문자 오발송에 직결되는 지표. 1순위.
2. **등록자 통과** (높을수록 좋음) — 미퇴실자 포착률.
3. 동률이면 **오식별** 낮은 쪽.

⚠ 한 접근이 다른 접근을 **모든 지표에서** 이기면 명확한 승. 트레이드오프(오통과 ↓지만 통과 ↓)면 위 우선순위로 판정한다. A는 잠정 채택이므로, B·C가 A를 지표로 이기면 교체 후보가 된다.

## 8. 강사 과제(A~E)와의 연결

8/18 강사 피드백으로 발표가 **"모델 성능 개선만"(8/25)**으로 재설정되면서 과제 A~E가 나왔다(`docs/pm/로드맵_고도화_방향.md` §3). 이 A/B/C 비교 체계가 그중 어디에 쓰이는지 못박는다 — 이 문서의 실측이 곧 과제 D의 "수치 근거"다.

| 과제 | 내용 | 이 문서·도구와의 연결 |
|---|---|---|
| **A. Rule vs Learning 점검** | 5종(YuNet→랜드마크→ArcFace-R100→AdaFace→TP-GAN)을 규칙/학습/혼합으로 분류 | 식별은 **learning(임베딩) + 규칙(코사인 임계값+margin) 하이브리드**다. rule-based 고정 임계값이 우리 CCTV 조건에서 실패한 실측 근거는 rules/05(클래스 내 거리 > 클래스 간 거리). "언제 감시할지"(탐지 창)는 rule-based로 분리 |
| **B. 파이프라인 자동화** | `webapp/tools/finetune/`를 수집→라벨링→학습→테스트 한 사이클로 자동화 | **테스트 단계 = 이 문서의 표준 평가(`eval_openset` + `regression_gate`).** 자동화 사이클의 마지막 칸에 이 커맨드(§4)가 그대로 들어간다 |
| **C. 클래스당 300장 + 증분 측정** | 인당 30장 → 300장, 100장 추가 시 성능 변화 측정 | 데이터가 바뀌면 **같은 고정 조건(§4)으로 재측정** — "300장이 30장보다 나은가"도 A/B/C와 같은 4지표·같은 게이트로 판정한다 |
| **D. 비포/애프터** | 현재 파이프라인 비포 → 고도화 애프터 비교, 8/25 발표자료 | **이 문서의 비교표(§5)가 애프터의 "수치" 그 자체.** 비포 = 6차 기준(78.1/3.9/11.9), 애프터 = A/B/C 최적안. 회귀 게이트 ✅ 블록을 발표에 캡처 |
| **E. 파이프라인 시각화** | 각 모델 입출력·신뢰도·속도 등 중간 단계 로깅·시각화 | 단계별 수치(YuNet 9.4ms·앙상블 167ms·유사도 분포·임계값)는 rules/05 실측 카드가 근거. 이 문서의 4지표가 "무엇이 개선됐나"의 정량 축 |

> **핵심**: 과제 D의 "비포/애프터 **수치**"는 감이 아니라 이 문서의 §5 비교표 + 회귀 게이트 판정이다. B·C 담당자가 §4 고정 조건을 지켜야 세 접근(그리고 비포)이 한 표에서 비교되고, 그 표가 곧 8/25 발표의 정량 근거가 된다.

### 배운 것 (다음 파인튜닝 시도의 출발점)

1. **개방집합 붕괴의 원인은 절대 코사인 인플레이션** — InfoNCE 단독은 배치 내 구분만 보장, loss가 0으로 붕괴하며 공간 스케일이 부풀어 절대 임계값 판정이 무너진다 (v1 실측으로 negative 다양성만으로는 부족함이 확정).
2. **앵커(distillation) 정칙화가 처방** — HR 임베딩을 원본 모델에 고정(`losses.embedding_anchor`, `train.py --anchor-weight`)하면 loss 0.065 유지·드리프트 0.048로 건강하게 수렴, 게이트 통과. 단 두 모델을 다 파인튜닝하면 인플레이션이 중첩되므로 금지.
3. **갤러리 위생 > 모델 수정** — 0814 세션 330장 제거 + 마스크·안경 보강(3명×60장, 맥캠 등록 화면)만으로 파인튜닝 최고치를 넘었다. 0814분은 `webapp/data/enroll_archived_0814/` 보관(8/31 파기 대상).

### 부록 — B안(Restormer 복원 전처리) 보류 확정 (2026-08-19 조사·실측, PR #169)

**결론: 진행하지 않는다.** 인식 모델을 재학습하지 않고 **입력 얼굴의 블러·노이즈를 복원한 뒤 기존 앙상블로 인식**하는 접근(Restormer)을 조사·사전검증한 결과, 전제가 데이터로 뒷받침되지 않았다.

- **블러–오류 상관이 약하다**: 부분상관 블러 미포함 표본 **-0.153**, 블러 포함 held-out 254장 **-0.067**(p=0.30) — 양쪽에서 **일관되게** 약함. "블러가 인식 오류의 주 원인"이라는 Restormer 채택의 근거 자체가 성립하지 않는다
- **§Phase 2가 독립적으로 같은 곳을 가리킨다**: 같은 주(8/21) Tier 2 파인튜닝 2사이클보다 **갤러리 정제·보강**이 이겼다. 병목은 *입력 이미지의 열화*가 아니라 **갤러리 데이터의 품질·다양성**이었다 — 서로 다른 각도의 두 실험이 같은 결론에 도달했다
- 조사 단계에서 세운 판단 기준도 남겨 둔다: ① 사람 눈에 선명한 복원이 신원 특징 보존을 뜻하지 않는다 ② 복원은 인식 모델을 안 바꿔도 **전처리에서 점수 분포와 개방집합 판정을 바꾼다** ③ 통과율보다 **미등록 오통과**를 우선 평가한다 (③은 파인튜닝 붕괴 2회로 비싸게 확인한 원칙과 같다)

**남긴 것**: 재현 가능한 감사 도구 `tools/blur_error_audit.py`·`tools/suggest_lowblur_labels.py`(+테스트)와 블러 포함 held-out 표본 구축 절차. 복원 계열이 다시 후보로 오르면 **이 도구로 같은 지표를 먼저 재측정**할 것 — 기각을 되풀이 조사하지 않기 위해 남긴다.
