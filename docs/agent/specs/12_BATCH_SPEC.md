## 0. 배치 공통 규칙

### 스케줄러 방식
- 상태: ✅ 결정
- 선택지 예: Spring @Scheduled / Spring Batch / node-cron / OS 스케줄러(작업 스케줄러, cron) / 클라우드 스케줄러
- 결정: **Spring `@Scheduled`** (backend 단일 인스턴스 내 실행)
- 이유: 출결 판정·알림의 주체가 Spring(backend)이라 데이터와 로직이 같은 곳에 있고, 별도 인프라 없이 이 규모(수강생 수십 명·단일 서버)에 충분. 분산 락(ShedLock 등)은 단일 인스턴스 전제이므로 도입하지 않음 — 다중 인스턴스로 확장 시 재검토
- 결정일: 2026-08-06

### 공통 실패 처리
- 상태: ✅ 결정
- 결정:
  - 실패 로그: backend 애플리케이션 로그 (레벨 ERROR, 배치 ID 포함)
  - 실패 알림: **연속 실패 임계 도달 시 1회 경고** (매 실패마다 보내지 않음 — 폴링 배치의 일시 실패는 다음 주기가 재시도 역할)
    - 발송 채널: **Slack** — BAT-002 미출석 알림이 이미 쓰는 그 채널 (2026-08-13 CTO 확정)
  - 실행 이력: `batch_runs` 컬렉션에 배치 ID·시각·성공 여부·처리 건수 기록 (판정 근거 추적용)
- 이유(알림 채널): **이미 붙어 있고 이미 검증된 경로**라서다. `SlackNotifierPort.sendText(String)`가 이미 있고, `SLACK_BOT_TOKEN`·`SLACK_CHANNEL_ID`도 `.env`에 있으며, 행정실 알림이 매일 그 채널로 나가고 있다. 새 채널을 열면 **시크릿이 하나 늘고, 실패 지점이 하나 늘고, 아무도 안 보는 곳이 하나 생긴다.** 후보였던 Discord·이메일은 셋 다 그 비용을 새로 치러야 한다
- ⚠ **배치 실패 알림에 개인정보를 넣지 않는다** — 배치 ID·연속 실패 횟수·마지막 오류 메시지까지다. 학생 이름·학번은 넣지 않는다 (rules/02 로깅 규칙). 미출석 알림과 같은 채널이라 "어차피 이름이 나가는 채널"로 착각하기 쉬운데, 그건 행정실이 봐야 할 업무 알림이고 이건 개발자용 장애 알림이다
- 결정일: 2026-08-06 (로그·이력) / 2026-08-13 (알림 채널)
- 구현 상태: 🔄 구현 완료, CTO 리뷰 대기 (#117, 2026-08-21)
  - 공용 컴포넌트: `global/batch/BatchFailureAlerter` — 5개 스케줄러(BAT-001·002·003·보존기간 스윕·
    문자 발송 대조) 전부가 공유한다. Slack 발송은 `SlackNotifierPort`를 직접 들지 않고
    notification의 인바운드 포트 `SendAdminMessageUseCase`(BAT-002 미출석 리포트와 같은 통로)로
    위임한다 — attendance·notification 두 도메인이 이 컴포넌트를 함께 쓰지만, 실제 Slack HTTP는
    항상 notification 안에서만 일어난다
  - ⚠ **연속 실패 카운터는 `batch_runs` 쿼리가 아니라 스케줄러별 인스턴스 필드(메모리)다** —
    지시서는 batch_runs 기반을 제안했지만, 문자 발송 대조 스케줄러가 notification 소유이고
    `batch_runs`는 attendance 소유 컬렉션이라(BAT-004 비고와 같은 이유) 거기 쓰면 소유권 경계가
    깨진다. 앱 전체가 이미 단일 인스턴스를 전제하므로(0장 스케줄러 방식 결정) 재기동 시 카운터가
    리셋되는 트레이드오프를 감수했다 — **PR #117 리뷰에서 CTO가 재검토할 수 있다**
  - 임계값은 배치 주기별 제안값(`batch.failure-alert.*`, PR에서 확정): 1분 tick 배치 4종은 5,
    하루 1회뿐인 보존기간 스윕은 1 (다음 기회가 24시간 뒤라 같은 숫자면 최대 5일 방치될 수 있다)

### BAT-001. LMS 당일 명단·출결 폴링

- **목적**: LMS 출결 API에서 당일 입실자 명단·출결 데이터를 주기적으로 가져와 우리 DB(`daily_roster`)에 적재한다. 대시보드·판정·알림은 LMS를 직접 조회하지 않고 **항상 이 컬렉션만 본다** (LMS 장애 시에도 마지막 동기화 상태로 화면 유지)
- **실행 주기**: `fixedDelay = 60초` 상시 실행 + 내부 시간대 가드 — 매 tick마다 현재 시각으로 LMS 호출 여부 결정. **시간대 경계는 고정값이 아니라 아래 "퇴실 시각 도출 규칙"으로 강의별 시각에서 계산한 합집합**:

  | 시간대 (Asia/Seoul, 평일) | LMS 호출 | 이유 |
  |---|---|---|
  | 입실 창 = ∪[강의 시작 −60분, +60분] | 5분에 1회 | 대시보드 갱신. 입실은 판정 시한(BAT-002 강의별 마감)까지 여유가 있어 분 단위 신선도 불필요 |
  | 퇴실 창 = ∪[강의 종료 −10분, +30분] | 매 tick (1분) | `checkedOut` 갱신이 "퇴실 미체크(DB 잔존)" 판정·카메라 포착 플로우의 기준 데이터 — 여기만 분 단위 신선도가 필요 |
  | 그 외 (주간 유휴) | 10분에 1회 | 늦은 태그 반영 (실측: 종료 3시간 뒤 퇴실 태그 사례 존재) |
  | 심야(마지막 퇴실 창 종료 ~ 첫 입실 창 시작)·주말 | 호출 안 함 | 데이터 변동 없음 |

- **실행 시간대 기준**: Asia/Seoul
- **상태**: ✅ 구현 완료 (2026-08-09 — 처리 1~9 / 2026-08-11 — `period` 화이트리스트·`daily_courses.period_end_date` 저장)

    `adapter/out/lms`(수집·변환) · `adapter/out/persistence`(적재)
  - ⬜ 잔여: **연속 실패 알림 채널**(0장 공통 규칙 미결정 — 코드에는 TODO로 표시)

#### 퇴실 시각 도출 규칙 (2026-08-07 CTO 확정)

수업 운영은 **오전반·오후반·야간반 3틀**이지만, **실제 퇴실 시각은 강의마다 다르다** — 배치 트리거를 3개 고정 시각으로 두면 어긋나는 강의가 생긴다 (2026-08-07 실측 근거 아래).

- **규칙: 강의별 퇴실 시각 `T_out`은 LMS `time` 필드의 종료 시각을 파싱해 사용한다** (예: `"09:20~18:10(총 8시간)"` → `18:10`). 입실 시각 `T_in`도 같은 방식으로 시작 시각을 파싱
- **반 구분은 `T_out`을 버킷팅해 표시용으로만 사용**: `~15:00` = 오전반 / `~20:00` = 오후반 / 그 이후 = 야간반. 판정·트리거는 언제나 강의별 `T_out` 기준
- **파싱 실패 시**: 해당 강의는 폴백 퇴실 시각(`LMS_DEFAULT_CHECKOUT_TIME`, 기본 18:00) 적용 + WARN 로그 — 형식이 바뀌어도 배치가 멈추지 않게 한다
- **`classDay=false`인 강의는 창 계산에서 제외한다** (2026-08-07 추가). 전 강의가 `false`면 합집합이 비고, 그러면 그날은 카메라도 배치 실호출도 돌지 않는다 — 공휴일·휴강 판단을 우리가 달력으로 관리하지 않고 LMS가 알려주는 대로 따른다는 뜻이다
  - 이 규칙이 생기면서 `DETECTION_WEEKDAYS_ONLY`(요일 하드코딩)는 **2차 방어선**이 된다. LMS가 응답하지 못한 날에도 주말이면 안 돌게 하는 용도로만 남긴다
- **카메라 탐지 창은 퇴실 창과 동일한 합집합**을 쓴다 — webapp이 내부 API(`/internal/detection-window`)로 받아 간다. `.env` `DETECTION_WINDOW`는 **비워 두는 폴백**이다(2026-08-11): 고정값은 시간표가 바뀌면 낡는다. 실제로 08-07 기준 6강의로 적어 둔 값이 08-11 실 LMS 9강의와 대조하니 **16:30~17:30 구간이 비어 있었다**(17시 종료 강의 2개의 퇴실 창 앞부분)

**2026-08-07 실측 (전 강의 6개)** — 3틀 고정 시각이 맞지 않는 근거:

| 강의 | LMS `time` | `T_out` | 반 버킷 | 실제 퇴실 태그 범위 |
|---|---|---|---|---|
| 자격증+사무행정실무 | 09:30~13:30 | **13:30** | 오전 | 12:23~13:25 |
| 컴퓨터활용능력2급 | 09:00~14:00 | **14:00** | 오전 | 13:50~13:54 |
| RAG·LLM·BPM 로우코드 | 09:10~18:00 | **18:00** | 오후 | 13:01~17:59 |
| 심화_AI 지능형 솔루션 (우리 과정) | 09:20~18:10 | **18:10** | 오후 | 18:01~18:20 |
| 일반기계기사 취득과정A | 09:20~18:10 | **18:10** | 오후 | 18:00~**21:04** |
| 회사에서 쓰는 엑셀실무 | 19:00~22:00 | **22:00** | 야간 | 21:52~21:53 |

- 퇴실 시각이 **5종**(13:30·14:00·18:00·18:10·22:00) — 13:00/18:00/22:00 고정 트리거였다면 사무행정(13:30)은 수업 중 판정, 컴활2급(14:00)은 4시간 지연, 우리 과정(18:10)은 10분 조기 판정
- 퇴실 태그는 `T_out` **직전 30분~직후**에 몰린다 → 퇴실 창을 `[T_out−10, T_out+30]`으로 잡는 근거 (#262에서 축소)
- 종료 3시간 뒤(21:04) 퇴실 태그 사례 존재 → **창 밖 지각 태그는 유휴 10분 폴링이 흡수** (최대 10분 내 반영)

**오늘 시간표 기준 계산 예시** (합집합 — 강의 시간표가 바뀌면 자동으로 달라짐):
- 입실 창: `08:00~10:30`, `18:00~20:00`
- 퇴실 창 = 카메라 탐지 창: `13:20~14:00`, `17:50~18:40`, `21:50~22:30`

#### LMS 출결 스냅샷 API 실스펙 (2026-08-06 실측 — CTO 확인)

- ⚠ 이 API는 인증 없이 공개 인터넷에 노출되어 있고 이름·생년월일을 포함한다 — 학원 측에 공유 예정. 우리 쪽 방어: URL 비커밋 + `birth` 미열람 + 입실자만 저장

##### 조기취업자 — 미출석 집계를 LMS 값으로 쓰는 이유 (2026-08-07 CTO 확정)

실응답에 `status="조기취업"`인 수강생이 있다. `checkInTime`이 null이라 **우리 도메인은 미출석으로 센다**. 그런데 LMS의 강의 레벨 `absent`에는 포함되지 않는다 — 한 강의가 `total 7 = present 5 + absent 1 + earlyEmployed 1`로 나뉜다.

- 우리가 직접 세면 미출석 5명, LMS `absent` 합계는 4명 — **조기취업자 1명만큼 어긋난다**
- 개인 `status`를 읽으면 구분되지만 화이트리스트 제외 필드다 (읽지 않기로 한 결정 유지)
- **결론: `daily_stats.absent_count`는 강의 레벨 `absent`의 합을 쓴다.** 강의 레벨 집계는 개인정보가 아니라 화이트리스트 원칙과 충돌하지 않고, 개인 필드를 읽지 않고도 정확해진다
- 명단(`daily_roster`) 쪽은 영향 없음 — 조기취업자도 `checkInTime`이 null이라 어차피 저장되지 않는다

#### 처리 내용

1. LMS 출결 스냅샷 API 호출 — 당일 전 강의 명단·출결 조회 (위 실스펙)
2. 경계면 네이밍 변환 (rules/09): 위 매핑표의 화이트리스트 필드만 snake_case로 추출 — `checkInTime`은 HHmm 문자열→시각 변환 포함
3. `daily_courses`에 **멱등 upsert** — 키 `(course_id, date)`. `time` 파싱으로 `class_start_time`·`class_end_time` 저장 (퇴실 창·BAT-003의 기준) + `classDay` 저장
4. **입실자 선별**: `checkInTime`이 있는 attendee만 대상으로 삼는다. **미출석자는 저장하지 않는다** (rules/04 행 최소화 — 결석자 개인정보를 우리 DB에 남기지 않는다)
5. 선별된 입실자를 `daily_roster`에 **멱등 upsert** — 키 `(student_id, date)`. 같은 데이터를 몇 번 받아도 결과 동일 (재시도·중복 호출 안전)
6. 퇴실 태그(`checkedOut=true`) 확인된 학생은 **개인정보 즉각 삭제** 원칙(rules/04) 적용 — roster 문서 삭제(TTL 인덱스는 백스톱). **roster에서 사라지는 것 자체가 "관리 대상 제외"** — 별도 제외 플래그를 두지 않는다
   - 이때 `checkoutStatus="조퇴"`면 삭제 전에 **EARLY_LEAVE 예외를 자동 등록**한다 (`source=LMS_AUTO` — BAT-003·API-005 참조). 제외는 이미 roster 삭제로 이뤄지므로, 자동 등록의 목적은 **대시보드 가시성·판정 근거 추적**이다
7. 정합성 검증 — **LMS 집계 ↔ 우리 계산을 4쌍 비교**한다. 불일치 시 WARN 로그 + 대시보드 경고 (수집 누락·API 이상 감지, 강사 요구 "데이터 수신 증명" 대응)

   | LMS 집계 | 우리 계산 | 이 비교가 잡아내는 것 |
   |---|---|---|
   | `total` | `attendees.length` | 응답 자체의 누락 |
   | `present` + `late` | `checkInTime`이 있는 수 | 입실 판정이 LMS와 어긋남 |
   | `checkedOut` | `checkedOut=true`인 수 | 삭제 대상 산정 오류 |
   | ~~`notCheckedOut`~~ | — | **🗑 대조 제외 (2026-08-11 실 LMS 실측)** — 아래 근거 |

   - `earlyLeave` ↔ 우리가 센 `checkoutStatus="조퇴"` 수도 함께 비교 (EARLY_LEAVE 자동 등록 누락 감지)
   - 이 검증은 "LMS가 틀렸나"가 아니라 **"우리 파이프라인이 제대로 세고 있나"** 를 매 tick 확인하는 장치다

   **`notCheckedOut` 대조를 뺀 이유 (2026-08-11 실연결 실측)**

   1. **의미가 다르다** — LMS는 **수업 중인 강의에도 0을 준다**. 20:00 실측에서 야간반(T_out 22:00)이
      재적 4명 전원 미퇴실인데 `notCheckedOut=0`이었다. 우리 값은 "지금 이 순간 잔존"이라 실시간
      대조가 성립하지 않는다. 17:45 실측에서도 수업 중인 4개 강의가 전부 어긋났다(우리 18·18·14·13 vs LMS 0)
   2. ⚠ **08-07의 "5쌍 전부 일치"는 착시였다** — 전원 퇴실한 뒤에 확인해 `0 = 0`이 우연히 맞은 것이다.
      **검증을 퇴실 후에만 돌리면 이 함정을 못 본다**
   3. **빼도 검증력이 줄지 않는다** — 우리 값은 `입실 − 퇴실`의 파생이고, 입실은 `present+late`가,
      퇴실은 `checkedOut`이 이미 각각 대조한다. 두 성분이 맞으면 이 값도 맞는다. 즉 **중복 검증이었다**
   - 남겨두면 수업 시간 내내 매 tick WARN이 강의 수만큼 쌓여 **진짜 경고가 묻힌다**
   - **`capacity` ↔ 우리 roster 수 비교는 하지 않는다** — 결석자만큼 차이 나는 것이 정상
8. 익명 집계 갱신: `daily_stats`에 입실·미퇴실·퇴실·미출석 **수치만** 기록 (미출석자 개인정보는 저장하지 않음). `absent_count`는 강의 레벨 `absent`의 합 — 위 "조기취업자" 항목 참조
9. 변경 발생 시 WebSocket(API-008)으로 대시보드 갱신 이벤트 발행

> **출석 판정은 이진** — `check_in_time` 존재 = 출석, 부재 = 미출석 (지각·유예 분류 없음. 공식 판정은 LMS 소관, 우리는 보조 시스템 — 99_DECISIONS 2026-08-06). 이 원칙 때문에 미출석자를 저장할 필요가 없다: "저장돼 있지 않다 = 미출석"이 곧 판정이다

#### 호출량 관리 (2026-08-07 CTO 확정 — rate limit 대응)

LMS 담당자가 공식 상한을 명시하지 않았으므로, **우리가 스스로 상한을 지키는 설계**로 간다.

- **응답이 전 강의 통합 스냅샷**이라 강의가 몇 개든 **호출 1회로 전부 커버**된다 — 강의별 개별 호출 없음
- 위 주기 기준 평일 예상 호출량 **≈ 400회/일** (퇴실 창 1분 ≈ 310 + 유휴 10분 ≈ 30 + 입실 창 5분 ≈ 55). 주말·심야 0회
- 모든 주기·창은 설정값이라 학원 요청 시 **코드 수정 없이 낮출 수 있다**
- **오발송 방지의 최종 안전장치는 폴링 주기가 아니라 "문자 발송 직전 최종 확인"**(rules/05 안전장치): 카메라 포착 → 문자 발송 직전에 LMS 1회 재조회로 퇴실 여부 최종 확인 후 발송. 문자는 하루 몇 건이라 호출 부담이 없고, **폴링이 늦어도 정상 퇴실자에게 복귀 문자가 나가는 사고를 원천 차단**한다
- ⚠ **"퇴실 1시간 전 최종 수신 후 폴링 중단"은 채택하지 않음** — 실측상 정상 퇴실 태그가 `T_out` 이후에 찍히므로(18:00~18:20, 늦게는 21:04), 그 시점에 폴링을 멈추면 정상 퇴실자를 "미퇴실"로 오판해 문자를 보내게 된다. 대신 `T_out−60`은 **관리 대상 확정 시점**으로 사용한다 (BAT-003)

#### 비고
- 시간대 경계·주기는 하드코딩하지 않고 설정으로: `application.yml` + `.env` (`LMS_POLL_INTERVAL_CHECKOUT=1m`, `LMS_POLL_INTERVAL_CHECKIN=5m`, `LMS_POLL_INTERVAL_IDLE=10m`, `LMS_DEFAULT_CHECKOUT_TIME=18:00`) — 구현 시 `.env.example` 갱신 필수. **창 경계 자체는 설정이 아니라 LMS `time` 파싱 결과**(퇴실 시각 도출 규칙)

### BAT-002. 미출석 확정·Slack 알림

- **목적**: **강의별 입실 마감**(강의 시작 + 유예) 시점의 미출석자를 확정해 행정실 Slack으로 알린다 (유저 스토리 ①③). **개인 문자는 발송하지 않음** — 문자는 퇴실 플로우("퇴실 미체크 AND 퇴실 시간대 카메라 포착")에서만 RPA로 발송 (99_DECISIONS 2026-08-05)
- **실행 주기**: `fixedDelay = 60초` + 강의별 마감 가드 — 매 tick마다 "현재 시각이 어떤 강의의 `시작 + 유예`를 지났는가"를 확인해 해당 강의만 처리. **고정 cron(09:30)이 아닌 이유는 강의 시작 시각이 과정마다 다르기 때문** (BAT-003이 강의별 `T_out − 60분`을 잡는 것과 같은 원리)
  - ⚠ **2026-08-18 실측이 계기**: 09:30 고정 cron이 아직 시작 전인 오후·저녁 과정 수강생까지 미출석 33명으로 알렸다. 마감 전 강의는 "미출석"이 아니라 "아직 입실 시간 전"이다
  - 유예는 설정값 `ATTENDANCE_ABSENTEE_GRACE_MIN`(기본 10분) — 기존 09:30은 "09:20 시작 + 10분"이었으므로 아침 과정의 알림 시각은 바뀌지 않는다
  - 같은 tick에 마감이 겹치는 강의들은 **한 메시지로 묶는다** (아침 09:20 시작 과정 여러 개 = 종전처럼 09:30 메시지 1건)
  - 마감의 상한은 `classEndTime` — 수업이 끝난 뒤의 미출석 알림은 행정 대응 시점을 놓친 뒤라 만들지 않는다 (이력 공백으로 남김). 휴강일(`classDay=false`)은 마감 자체가 없다
- **실행 시간대 기준**: Asia/Seoul
- **상태**: 🔄 개발중

#### 처리 내용

1. LMS 최종 폴링 1회 강제 실행 (BAT-001 로직 재사용) — 마감 직전 태그 누락 방지
2. **미출석자 추출은 LMS 응답에서 직접 한다** (`checkInTime`이 null인 attendee) — `daily_roster`에는 입실자만 있으므로 DB 조회로는 알 수 없다. 추출 결과는 **메모리에서만 다루고 저장하지 않는다** (rules/04 행 최소화). **추출 범위는 이번에 마감이 된 강의로 한정한다** — 스케줄러가 마감을 판정해 강의 목록을 넘긴다
3. **예외 등록 확인**: 당일 예외(외출·조퇴·병결 등, SCR-003에서 행정실 수동 등록) 있는 학생은 알림 대상에서 제외
4. 미출석자 명단 Slack 발송 — 강의별 그룹핑 + 시작 시각 표기 (예: "AI솔루션 (09:20 시작) 2명: 김OO·이OO"). **개인정보는 이 메시지로만 나가고 우리 DB에 남지 않는다**
5. 실행 이력 `batch_runs`를 **(BAT-002, courseId) 단위**로 저장 — 강의당 하루 1회 중복 방지 (재기동·수동 재실행에도 안전). 이력에는 발송 사실·건수만 남기고 미출석자 명단은 저장하지 않는다. 미출석 0명인 강의도 성공 이력을 남긴다(발송만 생략) — 이력이 없으면 다음 tick이 같은 강의를 다시 잡는다
6. 익명 집계: `daily_stats.absent_count` 갱신 (수치만)
7. 대시보드 상태 갱신 — 처리 1의 폴링이 명단을 바꾸면 그때 `roster_synced`가 나간다
   - **전용 이벤트를 새로 만들지 않는다 (2026-08-09 결정)**: 이 배치가 우리 DB에 남기는 변화는 처리 1의 폴링과 `daily_stats` 수치뿐이고, 미출석자 명단은 메모리에만 있다(처리 2). 화면이 다시 조회해야 할 이유는 폴링 결과가 전부라 `roster_synced` 하나면 충분하다. 아무것도 바뀌지 않은 날 "배치가 돌았다"는 이벤트만 보내면 클라이언트가 그때마다 API-003을 다시 부른다 — BAT-001이 "변경 있을 때만" 보내는 것과 같은 이유다

- **Slack 발송 결과 3분류** (2026-08-13 추가 — 실측 중복 발송 버그 원인):
  - **확정 성공**: Slack이 `ok:true` 응답 — 강의별 성공 이력 저장
  - **확정 실패**: Slack이 명시적으로 거절(`ok:false`, 토큰/채널 오류 등) — 실패 이력만 남긴다 = **다음 tick이 재시도**

- **중복 실행 방지**: `batch_runs`의 (date, BAT-002, courseId) 성공 이력 확인 후 skip
- **알림**: 최종 실패 시 ERROR 로그 + 실패 경고 발송 (Slack — 0장 공통 규칙, #117 구현 완료)

### BAT-003. 퇴실 관리 대상 확정

- **목적**: 강의별 퇴실 1시간 전에 "오늘 이 강의에서 퇴실을 찍어야 하는 사람"을 확정하고, 그 전에 이미 나간 사람(조퇴)을 관리 대상에서 정리한다. 퇴실 시간대 카메라 감시·문자 플로우가 **누구를 대상으로 도는지**를 명확히 하는 기준점 (2026-08-07 CTO 결정)

### BAT-004. 미퇴실 문자 재발송 tick

- **목적**: 미퇴실 상태가 유지되는 한 **카메라 재감지 여부와 무관하게** 시간 기준으로 복귀 요청 문자를 재발송한다. 재발송 트리거를 "감지 이벤트"에서 "시간 tick"으로 옮기는 것이 이 배치의 존재 이유다 (#189)
- **실행 주기**: `fixedDelay = 60초` 상시 실행 + 강의별 퇴실 창 가드. **재발송 간격 자체(10분)는 tick 주기가 아니라 `notification.sms.resend-interval` 게이트가 판단한다** — tick을 10분으로 두면 간격 경과 직후 최대 10분을 더 기다리게 되어 실제 간격이 최대 20분까지 벌어진다. 1분 tick + 10분 게이트로 두면 오차가 1분 이내다 (BAT-001~003과 같은 "자주 깨어나 매번 지금 할 때인가를 판단" 패턴)
- **실행 시간대 기준**: Asia/Seoul
- **상태**: 📝 설계

#### 처리 내용

1. `notifications`에서 **오늘 문자 발송 이력이 있는 학생**을 모은다 (상태 무관 — SENT·FAILED 모두). 학생별 **가장 최근 발송의 `alert_id`**를 함께 가져온다
2. 각 후보에 대해 `daily_roster` 잔존 여부 확인 — 없으면 skip (**퇴실했다는 뜻**, roster 삭제가 곧 대상 제외)
3. 해당 학생 **본인 강의의 퇴실 창**(`T_out−10 ~ T_out+30`)에 현재 시각이 들어가는지 확인 — 벗어나면 skip (`CheckCourseWindowUseCase`, #141과 같은 창)
4. `MissedCheckoutCommand`를 만들어 `HandleMissedCheckoutUseCase.handle()` 호출 — 이후 **횟수·간격 게이트, 발송 직전 LMS 재확인, 실제 발송·이력 기록은 기존 흐름을 그대로 재사용**한다
5. 학생 단위로 독립 처리 — 한 명의 실패가 다른 학생을 막지 않는다

#### 발송 대상의 전제 — 첫 문자는 이 배치가 보내지 않는다

이 배치는 **재발송 전용**이다. 오늘 문자 이력이 없는 학생은 후보에 들어오지 않는다.

문자 발송 조건은 **"퇴실 미체크(DB 잔존) AND 퇴실 시간대 영상 식별 포착"** 이중 조건이기 때문이다 (00_PROJECT·rules/07 필수 테스트 항목). 잔존만 보고 보내면 카메라에 한 번도 안 잡힌 학생 — 즉 이미 건물을 나갔지만 태그만 안 찍은 사람 — 에게도 복귀 요청이 나간다. 첫 발송의 트리거는 지금처럼 감지 이벤트(`MissedCheckoutEventListener`)가 유지하고, 이 배치는 **이미 이중 조건을 통과한 학생의 후속 발송만** 맡는다.

이 전제 덕분에 `MissedCheckoutCommand.alert_id`도 자연스럽게 정해진다 — **첫 발송이 쓴 그 알람 ID를 재사용**한다. 같은 미퇴실 건의 후속 발송이므로 `detection_alerts.sms_status` 갱신과 대조 폴링이 같은 알람을 가리키는 것이 맞다.

`camera_id`는 **null로 둔다.** 시간 기준 발송에는 대응하는 포착이 없기 때문인데, 실제로 이 필드는 Slack·RPA 어느 어댑터도 읽지 않아 문구·발송에 영향이 없다 (2026-08-20 확인).

#### 대상 데이터

| 입력 | 출력 | 예상 건수 |
|---|---|---|
| `notifications` 오늘 SMS 이력 + `daily_roster` 잔존자 + `daily_courses` 퇴실 창 | 복귀 요청 문자 재발송 + `notifications` 이력 + `detection_alerts.sms_status` 갱신 | tick당 후보 0~수 명, 실제 발송 0~1건 |

#### 실패 / 예외 처리

- **재시도**: 명시 루프 없음 — **1분 tick 자체가 재시도다** (BAT-002·003과 같은 원리). 실패해도 다음 tick이 같은 후보를 다시 잡고, 폭은 퇴실 창이 닫힐 때까지다
- **부분 실패 시**: 학생 단위 독립 처리. 한 명의 예외가 tick 전체를 중단시키지 않는다
- **중복 실행 방지**: `batch_runs`를 쓰지 않는다 — **중복 방지는 이미 `notifications` 이력이 하고 있다.** 횟수 게이트(최대 3회)와 간격 게이트(10분)가 발송 시도 기준으로 판단하므로, tick이 몇 번 겹쳐 돌아도 결과가 같다. `batch_runs`는 attendance 소유 컬렉션이라 notification이 쓰면 소유권 경계도 깨진다 (rules/04)
- **알림**: 실패 시 ERROR 로그 (0장 공통 규칙)

#### 실행 이력 기록
- 발송 이력은 기존 `notifications`에 그대로 남는다. 별도 배치 이력은 남기지 않는다 (위 중복 실행 방지 참조)

#### 비고
- **최대 3회 유지 + 간격 10분의 귀결**: 3통이 약 20분 안에 모두 소진된다 (2026-08-20 CTO 확정). 그 이후에는 퇴실 창이 남아 있어도 문자가 나가지 않는다 — "빠르게 3번 알리고 그만"이 의도된 동작이다. 더 길게 끌고 싶으면 간격이 아니라 `notification.sms.max-sends`를 올려야 한다
- **Slack은 그대로 하루 1회다** — `handle()` 안에서 Slack은 `alreadySentToday(SLACK)`로 막히므로 이 배치가 tick마다 돌아도 행정실 채널에 반복 알림이 쌓이지 않는다. 다만 첫 시도가 **실패**했다면 다음 tick이 다시 시도한다 (SENT 기록만 중복으로 치기 때문)
- **교차 강의 오탐 게이트, 첫 발송 경로에도 추가됨 (2026-08-21, #98)** — 이 배치(재발송)만 `CheckCourseWindowUseCase`로 본인 강의 퇴실창을 확인하고 첫 발송 경로(`MissedCheckoutEventListener`)엔 같은 게이트가 없어 비대칭이었다. 카메라 탐지창이 전 강의 합집합이라 아직 수업 중인 타 강의 학생도 그 시간대엔 잡히므로, 그 비대칭이 곧 오탐 원인이었다. 이제 `MissedCheckoutEventListener.dispatch()`도 roster 조회로 얻은 본인 `courseId`로 같은 창을 확인해, 창 밖이면 `handle()` 호출 전에 걸러낸다(DEBUG 로그). **실패 모드는 두 경로가 다르다**: 이 배치(BAT-004)는 창 조회가 예외를 던지면 `resendDue()`의 학생 단위 catch로 흡수돼 이번 tick만 건너뛰고 **다음 tick이 재시도**한다(위 "재시도" 항목과 동일). 첫 발송 경로는 재시도 tick이 없으므로, 같은 예외는 WARN 로그만 남기고 **현행대로 통과**시킨다 — `FinalCheckoutConfirmationAdapter`와 같은 fail-open 트레이드오프. 어느 경로든 게이트로 걸러진 알람의 `sms_status`는 (기존 roster-부재 skip과 동일하게) PENDING에 머문다. webapp 쪽 사진 기록의 교차 강의 오탐은 이슈 #98의 후속으로 남아 있다(오늘 범위 아님).
- **LMS 호출량**: 발송 직전 재확인(`confirmStillMissing`)은 두 채널 모두 보낼 것이 없으면 호출되지 않는다 (`handle()`의 순서 설계). 따라서 게이트가 닫힌 대부분의 tick은 LMS를 부르지 않는다
- **발송은 tick 스레드에서 하지 않는다**: `@Scheduled` 풀은 기본 1스레드라(SchedulingConfig) 여기서 Slack HTTP + 파이썬 서브프로세스(최대 9초)를 돌리면 BAT-001 폴링까지 밀린다. 감지 경로가 쓰던 단일 스레드 실행기(`NotificationDispatchExecutor`)를 **공유**해 넘긴다
- **실행기를 공유하는 것이 핵심이다**: 두 트리거가 각자 스레드를 들면 같은 학생에 대해 감지 경로와 tick 경로가 **동시에 게이트를 통과해 문자가 두 번 나갈 수 있다.** 스레드가 하나여야 발송 판정(`alreadySentToday`·`smsSendAllowed`)이 순서대로 평가된다
- **tick이 겹쳐 쌓이지 않게 한다**: 앞 tick의 작업이 아직 처리 중이면 이번 tick은 건너뛴다. 발송 1건이 최대 9초라 후보가 여럿이면 1분을 넘길 수 있고, 그대로 매분 밀어 넣으면 큐가 자란다. 건너뛰어도 손해가 없다 — 다음 tick이 같은 후보를 다시 잡는다
- **끄는 방법**: `notification.sms.resend-enabled=false` (기본 true)

### BAT-005. T_out+5 1차 판정 일괄 발송

- **목적**: 퇴실 시각 직후(T_out+5분)에 LMS 태그/미태그 상태만으로 미퇴실자를 확정하고, **카메라 감지 없이** 즉시 복귀 요청 문자를 보낸다. 기존 첫 발송 트리거(카메라 감지 이벤트)에서 퇴실 시간대 화장실·옥상 이용자가 반복 포착돼 오발송되는 문제를 해결하기 위해 도입 (#262)
- **실행 주기**: `fixedDelay = 60초` + 강의별 T_out+5분 가드 — 매 tick마다 "현재 시각이 어떤 강의의 `T_out+5`를 지났는가"를 확인해 해당 강의만 처리. 상한은 `T_out+30`(퇴실 창 종료) — 그 이후는 의미를 잃는다
- **실행 시간대 기준**: Asia/Seoul
- **상태**: 🔄 개발중

#### 처리 내용

1. LMS 최신 폴링 1회 강제 실행 (BAT-001 로직 재사용) — 판정 직전 최신 태그 반영
2. 해당 강의의 잔존자(daily_roster) 전원 추출 = 미태그자 전원
3. 당일 예외 등록자 제외
4. 남은 학생에게 `HandleMissedCheckoutUseCase.handle()` 호출 — Slack 알림 + 복귀 요청 문자 발송. **alertId=null, cameraId=null** — 카메라 탐지 없이 발송하므로 detection_alerts가 없다
5. 발송 이력(notifications)을 남기므로 BAT-004(재발송 tick)가 이 학생들을 후보로 잡는다

#### 기존 흐름과의 관계

- **BAT-004 연동**: BAT-005의 발송 이력에는 alertId가 null이다. `findTodaySmsResendCandidates()`가 null alertId 이력도 포함하므로 BAT-004가 시간 기반 재발송을 담당한다. `MissedCheckoutService.handle()`은 alertId null을 안전하게 처리한다 — `alertOutcomePort`·`realtimeNotifierPort` 호출을 건너뛴다
- **카메라 감지 경로**: 기존 `MissedCheckoutEventListener`는 그대로 유지된다. BAT-005가 먼저 발송했다면 `alreadySentToday(SLACK)`·횟수 게이트가 중복 발송을 막는다
- **발송은 `NotificationDispatchExecutor`를 공유한다**: BAT-004·카메라 감지 경로와 같은 단일 스레드 실행기로 넘긴다 — 같은 학생에 대한 동시 게이트 통과를 방지한다

#### 대상 데이터

| 입력 | 출력 | 예상 건수 |
|---|---|---|
| `daily_roster` 해당 강의 잔존자 + `attendance_exceptions` 당일 예외 | 복귀 요청 문자 + `notifications` 이력 | 강의당 0~수십 명 |

#### 실패 / 예외 처리

- **재시도**: 명시 루프 없음 — 1분 tick 자체가 재시도다. 실패한 강의는 성공 이력이 없으므로 다음 tick이 다시 잡고, 폭은 퇴실 창 종료(T_out+30)까지다
- **부분 실패 시**: 강의 단위로 독립 처리 — 한 강의의 실패가 다른 강의를 막지 않는다. 학생 단위로도 독립 — 한 명의 발송 실패가 나머지를 막지 않는다
- **중복 실행 방지**: `batch_runs`의 (date, BAT-005, courseId) 성공 이력 확인 후 skip
- **알림**: 연속 실패 임계 도달 시 Slack 경고 1회 (0장 공통 규칙, `BatchFailureAlerter`)

#### 실행 이력 기록
- `batch_runs`에 강의별 기록 (시각·강의 ID·잔존 수·예외 제외 수·발송 수)

#### 비고
- **끄는 방법**: `notification.first-checkout-alert.enabled=false` (기본 true)
- **tick이 겹쳐 쌓이지 않게 한다**: BAT-004와 같은 `AtomicBoolean inFlight` 가드 — 앞 tick이 아직 처리 중이면 건너뛴다
- **퇴실 창 축소와 함께 도입됐다** (#262): 퇴실 창이 `[T_out−30, T_out+60]`에서 `[T_out−10, T_out+30]`으로 줄어들며 카메라가 화장실·옥상 이용자를 잡는 시간대도 줄었다. 대신 T_out+5에 LMS만으로 일괄 판정해 카메라 의존을 없앤다
